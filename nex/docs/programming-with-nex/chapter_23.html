Chapter 23

Modules and Files

Until now, most examples have fit in one file or one REPL session. Real programs do not. They are split into multiple classes and files, with clear boundaries between parts of the system.

In Nex, the main tool for bringing code from another Nex file into the current program is intern.

Why Split a Program

Splitting a program across files is not mainly about size; it is about design. Put code in a separate file when:

  • it represents a distinct concept
  • it can be understood independently
  • it should be reused elsewhere
  • keeping it separate makes the boundary clearer

A Bank_Account class and a Report_Printer class should not live in one file merely because both belong to the same application. They are different concepts with different reasons to change.

The intern Statement

Nex loads classes from other files with intern:

intern math/Calculator

This means: find the Nex file for Calculator under the math path and make that class available in the current program.

An alias may also be given:

intern math/Calculator as Calc

That allows the imported class to be referred to locally as Calc.

How intern Resolves Files

intern searches in this order:

  1. the directory of the currently loaded script, if the code came from a file
  2. the REPL or process working directory
  3. ~/.nex/deps

For a path-qualified intern such as:

intern net/Tcp_Socket

Nex tries these local layouts under each search root:


lib/net/Tcp_Socket.nex
lib/net/tcp_socket.nex
lib/net/src/Tcp_Socket.nex
lib/net/src/tcp_socket.nex

Then it tries the same path forms under:

~/.nex/deps

So all of these are valid examples:

./lib/net/tcp_socket.nex
/some/project/lib/net/Tcp_Socket.nex
~/.nex/deps/net/tcp_socket.nex
~/.nex/deps/net/src/Tcp_Socket.nex

Exact-case filenames are checked first. If they are not found, Nex falls back to a lowercase filename such as tcp_socket.nex.

A Simple Two-File Example

Suppose lib/math/Counter.nex contains:

class Counter
create
  make
  do
    count := 0
  end
feature
  count: Integer
  increment
  do
    count := count + 1
  end
  value: Integer
  do
    result := count
  end
end

Another file may use it with:

intern math/Counter

class Main
create
  make
  do
    let c := create Counter.make
    c.increment
    c.increment
    print(c.value)
  end
end

The point is that Counter now has its own module boundary. It can be read, tested, and reused on its own.

Namespaces and Ambiguous References

The path in intern path/Class is not only a way to find a file. It also becomes that class's namespace. Two libraries can each define a class named Account without conflict, right up until a single program interns both of them:

intern finance/Account
intern billing/Account

let a := create Account.make(1)

Nex does not guess which Account is meant here, and it does not let whichever library happened to load first silently win. It rejects the program at compile time:

Ambiguous reference to 'Account': interned from billing.Account and finance.Account.
Reference one directly by its qualified name (e.g. billing.Account), or rename it
on the way in with a path-qualified `intern ... as`.

The fix is to write the class's full name — the same path/Class form used on the intern line — anywhere the class name would otherwise appear: in a type annotation, in create, in inherit, or in a match clause.

intern finance/Account
intern billing/Account

let a: finance/Account := create finance/Account.make(1)
let b: billing/Account := create billing/Account.make(2)
print(a.balance)
print(b.id)

Both classes are now usable in the same program, each referred to unambiguously by its own qualified name. Two things are worth noting about how this behaves:

  • A class declared directly in the current file always wins over an interned one of the same name. Ambiguity is only ever between two interned classes — an unrelated library update can never silently break code that already worked by introducing a name clash with something you defined yourself.
  • If two different intern paths happen to lead to the same file — two libraries that both depend on a third and each intern it — that is not a collision. It is one class, reachable two ways.

A bare, unqualified name — no path at all, like a plain intern Logger — never collides with anything else brought in the same way, so this only comes up once a program starts interning path-qualified libraries.

Aliases

Aliases are useful when:

  • the imported name is long
  • two imported classes would otherwise collide
  • a local short name improves readability

Library names are often long for a good reason. Suppose a shipping library has both Domestic_Rate_Table and International_Rate_Table. Inside the library, the full names are needed to tell the two apart. A program that only ever ships abroad has no such confusion, so it can use a short name:

intern shipping/International_Rate_Table as Rate_Table

let rates := create Rate_Table.make("EUR")
print(rates.rate_for(2.0))

Use aliases sparingly. The goal is clarity, not abbreviation for its own sake. A reader who meets Rate_Table can find what it stands for in the intern line at the top of the file.

Aliasing to resolve a collision

A path-qualified alias is also a second way out of the ambiguity in the previous section — rename one side of a collision (or both) on the way in, and each alias refers unambiguously to its own class from then on:

intern finance/Account
intern billing/Account as Billing_Account

let b := create Billing_Account.make(2)
print(b.id)

Billing_Account reaches billing's class directly, without ever touching the name it collides on. The bare name Account is unchanged, though: it is still ambiguous, so it must not be used while both classes are interned. To refer to both classes by short names, alias both sides:

intern finance/Account as Finance_Account
intern billing/Account as Billing_Account

let a := create Finance_Account.make(1)
let b := create Billing_Account.make(2)

Aliasing only helps this way when the intern being renamed is path-qualified; aliasing a bare, unpathed intern is purely for shortening or readability, since there is no path to disambiguate with.

Free Functions and intern

intern brings in a unit's free functions exactly as it brings in its classes — the whole file, not only the one name written after the path. A function sharing a file with an interned class arrives alongside it, under its own bare name, whether or not you ever use it.

A function's qualified name is the directory path of the intern followed by the function's own name — not the file's name. Interning trade/shipping, whose file defines ship, makes the function callable as trade.ship.

But a function has none of the escape hatches above: as only ever renames a class. Given two warehouses that each define a ship function, rounding a shipment quantity a different way:

-- trade/ship.nex
function ship(qty: Integer): Integer
do
  result := qty + 1
end

-- other/ship.nex
function ship(qty: Integer): Integer
do
  result := qty - 1
end
intern trade/ship
intern other/ship

print(ship(10))

a bare call is rejected the same way a bare class reference is:

Ambiguous reference to 'ship': interned from other.ship and trade.ship.
Call one directly by its qualified name, e.g. other.ship(...).

The fix looks similar to a class's qualified name, but is spelled differently — with . rather than /:

intern trade/ship
intern other/ship

print(trade.ship(10))  -- 11
print(other.ship(10))  -- 9

The different spelling is forced by syntax, not chosen for style. A class's path/Class could only appear in a type annotation, a create, an inherit, or a match clause — never in the middle of an ordinary expression, so / can be used there without being mistaken for division. A function call is an ordinary expression, and / already means division inside one, so a qualified call instead reuses . — the same character an ordinary method call already uses.

trade.ship(…) parses exactly like a method call on a variable named trade. Nex reads it as a qualified call unless trade is bound where the call appears — a local, parameter, or field of that name in the enclosing routine or class, or a global or class of that name. A local only shadows the module inside the routine that declares it:

intern trade/ship

function use(trade: Integer): Integer
do
  result := trade + 2
end

print(trade.ship(10))  -- 11

The parameter trade belongs to use alone, so the top-level call still reaches the module. Inside use, however, trade.ship(…) would be an ordinary member access on the parameter — avoid reusing an intern path segment as a local name in a routine that also calls that module.

A multi-segment path is written the same way, using . separated names:

intern trade/core/ship

print(trade.core.ship(10))

As with classes, none of this is needed until two interned functions actually collide. Most of the time a function is simply called by its bare name, exactly as before.

Designing Module Boundaries

A good file boundary usually matches a good class boundary. In Nex, the class is the unit of meaning. It has a name, a set of features, and contracts that say what it promises. A file built around one such class is easy to describe, and intern already works this way: intern finance/Account looks for a file named after the class. So the natural starting point is one main class per file, with the file named after it.

A file can still hold more than one class. What matters is whether a second class has an identity of its own. Interval_Cursor in Chapter 15 exists only so that across can walk an Interval. No other code creates one, and it changes whenever Interval does, so it belongs in Interval’s file. Transaction in the ledger example below is different. Accounts use it, but so may reports, imports, and tests, each in its own way. It is a concept in its own right, so it gets its own file.

The layout to avoid is the “misc” or “utils” file, where routines go because they had nowhere else to live. Its name tells a reader nothing about what is inside it. It also costs more in Nex than it might seem. intern brings in a whole file, every class and free function in it. It also brings in everything that file interns, all visible under their bare names. So a program that interns a grab-bag file for one helper gets all the others too, and each extra name is another chance of an ambiguous reference (Section 23.5).

Before settling on a file, it helps to answer three questions about it:

  • What concept does it define? If the answer needs an “and”, as in “accounts and report formatting”, the file probably holds two concepts.
  • Who needs to know about it? The files that intern it are its clients. They should need only its public features and its contracts.
  • What can stay hidden? Helper routines and fields that clients have no reason to touch belong in a private feature section (Chapter 12). The less a file exposes, the more freely it can change later.

Answered well, these questions make the file layout a summary of the design. Someone new to the program can list the files and learn what concepts it is built from before reading any code.

What Belongs Together

A useful test for whether two pieces of code belong in the same file is to ask what would make each of them change. Code that changes for the same reason belongs together. Code that changes for different reasons belongs apart.

The booking program of Chapter 22 shows the test at work. It has three parts:

  • Request, together with parse_count and parse_request. The two functions exist only to turn text into a Request. If the format customers type changes, all three change together, so they share one file, booking/Request.nex.
  • Show, which changes when the rules for seats or the way bookings are saved change. Neither change has anything to do with how a request is typed, so it gets its own file, booking/Show.nex.
  • handle_request, the desk, which connects the other two. It is the part of the program a user meets, and it changes when the conversation with the customer changes. It lives in the main program file, which interns the other two.

Now picture the opposite: Stack, Customer, and Image_Loader in a single file. Each changes for its own reason. Someone editing how customers are stored has to work around a stack and an image loader, and someone looking for Customer would never think to open a file named after a stack. Worse, a program that only wanted a stack would also bring in Customer, Image_Loader, and whatever graphics library Image_Loader interns.

The same test rules out grouping code by when it was written. A file of “features added this month” holds code that has nothing in common except its date, and it gets harder to understand every month. If you notice code being grouped that way, take it as a sign that the concepts have not been named yet, and name them.

The aim is a file layout that reduces how much a reader must hold in mind at once. Opening a file should hold no surprises: its name says which concept is inside, and everything inside serves that concept.

Intern and Contracts

Once a class lives in another file, often written by someone else, its users stop reading its code. A program that interns bank/Account sees a name and a list of features, and must decide from those alone how to use it. The question is what it can rely on without opening the file.

The contracts are the answer. Here is Account as its author might write it:

class Account
create
  make(name: String)
  do
    owner := name
  end
feature
  owner: String
  balance: Real

  deposit(amount: Real)
  require
    positive_amount: amount > 0.0
  do
    balance := balance + amount
  ensure
    increased: balance = old balance + amount
  end

  withdraw(amount: Real)
  require
    positive_amount: amount > 0.0
    enough_funds: amount <= balance
  do
    balance := balance - amount
  ensure
    decreased: balance = old balance - amount
  end
invariant
  never_negative: balance >= 0.0
end

A user of this class needs only the headers and the contracts. The require clauses say what the caller must check before each call. The ensure clauses say what each call achieves, and the invariant says what is always true of an account. The bodies, the lines between do and ensure, are the author’s business. They can be rewritten at any time, and callers are unaffected as long as the contracts still hold.

Nex can produce this outside view for you. nex doc reads a file and writes a summary of each class’s features with their contracts, and leaves out the bodies:

$ nex doc lib/bank/Account.nex Account.md

For withdraw, the summary lists the parameter amount: Real, the preconditions positive_amount and enough_funds, and the postcondition decreased. That is everything a caller needs and nothing a caller should depend on.

Contracts also settle who is at fault when something goes wrong across the boundary. Suppose a program withdraws more than the balance:

intern bank/Account

let a := create Account.make("Ada")
a.deposit(100.0)
a.withdraw(150.0)

Running it reports:

Error: Precondition violation: enough_funds
  The call at line 5 does not meet the precondition `enough_funds` of Account.withdraw.

The message points at line 5 of the calling program. The bug is on the caller’s side of the boundary, and there is no need to look inside Account at all. If instead withdraw took the wrong amount from the balance, the failure would name the routine in the other file:

Error: Postcondition violation: decreased
  Account.withdraw, called at line 5, does not deliver its postcondition `decreased`.

Here the call was correct, and the bug is in Account. Either way, the boundary between the two files is also the boundary of responsibility, and the error message says which side broke the agreement.

A Worked Example: Splitting a Small Ledger

A small ledger program records the money going in and out of an account and prints statements. It is built from three concepts: a single Transaction, an Account that collects transactions, and a Ledger_Report that presents an account to a reader. Applying the tests from the last few sections gives this layout:

ledger/
  main.nex
  lib/finance/Transaction.nex
  lib/finance/Account.nex
  lib/finance/Ledger_Report.nex

Each library file holds one class and is named after it, so intern finance/Account finds lib/finance/Account.nex (Section 23.3). The interesting part is the reasoning behind each boundary, so take the files one at a time.

finance/Transaction.nex

class Transaction
create
  make(d: String, a: Real)
  do
    description := d
    amount := a
  end
feature
  description: String
  amount: Real
end

A transaction could have been a pair of fields inside Account. It gets a class and a file of its own because other code deals with transactions directly: the main program creates them, the report lists them, and an import from a bank file would produce them. It is a concept in its own right, not a detail of accounts.

finance/Account.nex

intern finance/Transaction

class Account
create
  make(name: String)
  do
    owner := name
    entries := []
  end
feature
  owner: String
  entries: Array[Transaction]
  add_entry(t: Transaction)
  do
    entries.add(t)
  end
  balance: Real
  do
    result := 0.0
    across entries as entry do
      result := result + entry.amount
    end
  end
end

Account interns Transaction because its fields and routines are written in terms of it. The dependency goes one way only: a transaction knows nothing about the accounts that hold it.

finance/Ledger_Report.nex

intern finance/Account

class Ledger_Report
feature
  print_balance(a: Account)
  do
    print(a.owner + ": " + a.balance.to_string)
  end

  print_statement(a: Account)
  do
    print("Statement for " + a.owner)
    across a.entries as entry do
      print("  " + entry.description + ": " + entry.amount.to_string)
    end
    print_balance(a)
  end
end

This is the boundary that most needs a reason. print_balance and print_statement could easily have been methods of Account, and the program would work just the same. Apply the test from Section 23.8: what makes each piece change? Account changes when the rules about money change, for example to forbid an overdraft or to add interest. The report changes when someone wants the output to look different, such as aligned columns, a currency symbol, or a statement for one month only. Those are different reasons, often coming from different people, so they belong in different files. As a bonus, a second kind of report, say one that writes a CSV file, can be added without touching Account.

Finally, the main program ties the pieces together:

intern finance/Transaction
intern finance/Account
intern finance/Ledger_Report

let a := create Account.make("Ada")
a.add_entry(create Transaction.make("salary", 3000.0))
a.add_entry(create Transaction.make("rent", -1200.0))

let report := create Ledger_Report
report.print_statement(a)
$ nex main.nex
"Statement for Ada"
"  salary: 3000.0"
"  rent: -1200.0"
"Ada: 1800.0"

Strictly, the first two intern lines are not needed. As Section 23.7 explained, a file brings in everything it interns, so intern finance/Ledger_Report alone would make Account and Transaction available too, and the program would run the same. Write them anyway. main.nex uses all three classes by name, so it should say so. If it relied on the chain instead, its correctness would depend on how the other files happen to be written today. Suppose a later version of Ledger_Report worked only with account summaries and stopped interning Account. Then main.nex would break, even though nothing it uses had changed. The rule is to intern every class you name. Interning a file that also arrives through another file is harmless, because it is the same class reached two ways.

Extending a Class from Another File

Sometimes the class that needs a new feature is not yours to edit. It comes from a library, or from a module another part of the program owns. Suppose a report needs the average amount of an account’s entries, and finance/Account is shared code you would rather not change. A free function average_entry(a) would work, but then callers write a.balance for one question about an account and average_entry(a) for the next.

An extend block adds features to an existing class from outside its file:

intern finance/Transaction
intern finance/Account

extend Account
feature
  average_entry: Real
  require
    has_entries: not entries.is_empty
  do
    result := balance / entries.length.to_real
  end
end

let a := create Account.make("Ada")
a.add_entry(create Transaction.make("salary", 3000.0))
a.add_entry(create Transaction.make("rent", -1200.0))
print(a.average_entry)     -- 900.0

Inside an extension, the body is written as if it were in the class itself. balance and entries are the account’s own features, used by name without qualification. As in a regular method, this refers to the account the feature was called on, so balance could equally be written this.balance.

Callers now write a.average_entry, as if Account had declared it. The feature is inherited by heirs of Account, its precondition is checked like any other, and Account’s invariant is checked around the call. Calling it on an account with no entries fails at the caller, as a precondition should. Add two lines to the end of the program:

let empty := create Account.make("Bo")
print(empty.average_entry)

The second of them is line 19 of the program, and that is where the error points:

Error: Precondition violation: has_entries
  The call at line 19 does not meet the precondition `has_entries` of Account.average_entry.

An extension is written by a client of the class, not by its author, and the rules follow from that:

  • it sees only the class’s public features; a private one is not visible in its body
  • it cannot assign the class’s fields; it changes an object only by calling the class’s own routines
  • it adds routines only: no fields, constructors or invariants
  • it cannot replace a feature the class already has, and two extensions cannot add the same feature

So an extension can never break a class: everything it does goes through the class’s own contracts.

Adding an Operation to a Family of Classes

Extensions matter most for a family of classes. Suppose a geometry/Shapes module declares a deferred Shape with two heirs, Circle and Rect. The heirs are small and only make sense as members of the family, so they share the file with Shape:

geometry/Shapes.nex

deferred class Shape
end

class Circle inherit Shape
create
  make(r: Real)
  do
    radius := r
  end
feature
  radius: Real
end

class Rect inherit Shape
create
  make(w, h: Real)
  do
    width := w
    height := h
  end
feature
  width: Real
  height: Real
end

The file holds no class called Shapes. Like intern trade/ship in Section 23.6, whose file holds only a function, the intern path names a file, and everything in that file comes in.

A second module, geometry/Areas, adds an operation to the whole family without touching Shapes.nex:

geometry/Areas.nex

intern geometry/Shapes

extend Shape
feature
  area: Real
  deferred
  ensure
    non_negative: result >= 0.0
  end
end

extend Circle
feature
  area: Real
  do
    result := 3.14159 * radius * radius
  end
end

extend Rect
feature
  area: Real
  do
    result := width * height
  end
end

area is deferred in Shape, so every concrete heir must have one, and each implementation inherits the postcondition. A call s.area on a Shape dispatches on the object’s class, as for any routine.

Now a third module, geometry/Triangles, adds a new heir, Triangle, knowing nothing about areas:

geometry/Triangles.nex

intern geometry/Shapes

class Triangle inherit Shape
create
  make(b, h: Real)
  do
    base := b
    height := h
  end
feature
  base: Real
  height: Real
end

A program that interns both geometry/Areas and geometry/Triangles is rejected:

Type error in .../geometry/Triangles.nex: Class 'Triangle' does not implement
deferred feature 'area', declared by 'extend Shape' at .../geometry/Areas.nex,
line 3. Add 'extend Triangle feature area ... end', give 'area' a default body
in 'extend Shape', or declare 'Triangle' 'deferred'.

Neither module is wrong on its own. The gap appears only when the two meet, so the program that brings them together supplies the missing piece:

intern geometry/Shapes
intern geometry/Areas
intern geometry/Triangles

extend Triangle
feature
  area: Real
  do
    result := base * height / 2.0
  end
end

let shapes: Array[Shape] := [create Circle.make(1.0), create Rect.make(2.0, 3.0), create Triangle.make(4.0, 3.0)]
across shapes as s do
  print(s.area)
end
3.14159
6.0
6.0

The program interns geometry/Shapes as well, even though both other modules bring it in. It names Shape, Circle and Rect itself, and, as the ledger example showed, a file should intern every class it names.

I think we should pause a bit and let the idea sink in. A family of classes can grow in two directions: new heirs, and new operations on all of them. Inheritance makes the first easy and the second hard; a match over a union does the opposite. Language designers call this conflict the expression problem, a name Philip Wadler gave it in 1998: how to add both new cases and new operations without editing existing code, while the compiler still checks that every case has every operation. Extensions are Nex’s answer. Both kinds of growth are easy, neither requires editing existing files, and the compiler still guarantees that every heir has every deferred operation. The check happens when modules are combined. That is why the program that brought geometry/Areas and geometry/Triangles together had to supply Triangle’s area: someone must write each missing pairing, and Nex makes sure nobody forgets one. When not every heir should have an operation, give the Shape extension a default body instead of deferred, and let the heirs that can do better redefine it.

Extending Built-in Types

Built-in types can be extended the same way as user-defined classes. Let's see how the String type can be extended with a query that does the palindrome check:

extend String
feature
  is_palindrome: Boolean
  do
    let s := to_lower
    result := true
    from
      let i := 0
    until
      i >= length / 2
    do
      if s.char_at(i) /= s.char_at(length - 1 - i) then
        result := false
      end
      i := i + 1
    end
  end
end

print("Level".is_palindrome)     -- true
print("Nex".is_palindrome)       -- false

Because length and to_lower name features of String, a local of the routine may not use those names.

A generic built-in type is extended with its own parameter names, and a constraint limits an extension to some type arguments:

extend Array [T -> Comparable]
feature
  maximum: T
  require
    not_empty: not is_empty
  do
    result := get(0)
    across this as x do
      if x > result then result := x end
    end
  end
end

print([3, 9, 4].maximum)                     -- 9
print(["pear", "apple", "plum"].maximum)     -- "plum"

Calling maximum on an array of objects that are not Comparable is a compile-time error. An extension of Any gives a feature to every value, and one of Comparable to every comparable value, your own classes included. Note that an extension of Real does not apply to Integer values: an Integer is converted where a Real is expected, but it is not a kind of Real.

Extensions work in the REPL as well: an extend input adds its features to a class an earlier input declared.

When to Extend

If you own a class and the feature belongs to its concept, put the feature in the class. An extension is for the cases where that is not possible or not right: a library class, a built-in type, or an operation that belongs to a different module than the classes it applies to, as area belongs to geometry/Areas rather than to geometry/Shapes. Keep each extension in the module whose concept it serves, and resist spreading one class across many files: a reader should still be able to find a class’s features.

Summary

  • Split programs into files to express design boundaries, not merely to reduce length
  • Use intern path/Class_Name to load Nex classes from other files
  • The path in intern path/Class is also the class's namespace: two interned classes with the same bare name are a compile-time ambiguous reference error, never a silent guess
  • Resolve a collision by writing the class's qualified name (path/Class) directly, or by giving one side a path-qualified alias with as
  • A class declared in the current file always wins over an interned one of the same name; only two interned classes can collide
  • Use as when a local alias improves clarity, even without a collision
  • intern brings in a unit's free functions the same way it brings in its classes, but a function cannot be renamed with as; a colliding bare call is an ambiguous reference too, resolved instead with a qualified call — path.name(…), spelled with . rather than / because a function call, unlike a class reference, is an ordinary expression where / already means division
  • A qualified call is read that way unless its leading name is bound where the call appears — a local, parameter, or field in the enclosing routine or class, or a global or class of that name; a local shadows the module only inside the routine that declares it
  • Good file boundaries usually follow good class boundaries
  • Contracts make multi-file code easier to trust and reuse
  • A clean module layout reduces coupling and mental overhead
  • extend Class feature ... end adds routines to a class from another file; an extension is a client of the class, sees only its public features, and adds no state
  • A deferred feature an extension adds must be implemented by every concrete heir in the program, so new operations and new heirs can both be added without editing existing files
  • Built-in types can be extended too, generic ones with their own parameter names and optional constraints, as in extend Array [T -> Comparable]
