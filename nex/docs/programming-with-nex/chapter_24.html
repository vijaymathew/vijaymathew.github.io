Interoperability

A practical language is not an island. Sooner or later a program needs to talk to a database, a graphics subsystem, or an external service. Nex is designed for that reality. It can import additional types and objects from the host-platform.

Importing Platform Symbols

Nex supports the top level import statements for bringing in host libraries. For example on the JVM:

import java.util.Scanner

These imports are primarily meaningful when compiling Nex programs. They tell the JVM compiler which host symbols the program expects to use.

In the last chapter we used intern to load external Nex classes and functions. In contrast, import loads external Java symbols. So keep the distinction in mind:

  • use intern for Nex-to-Nex modularity
  • use import for host-platform interop

A Nex class is part of your program’s design. An imported host symbol is part of the surrounding environment.

Working with Java

There are four ways for a Nex program to work with Java code. It can use Java objects directly. It can implement a Java interface, so that Java code can call back into Nex. It can extend a Java class. And it can add features of its own to a Java class. Let's take each of them, in that order. Each technique comes with a pattern that keeps the Java side of the program small, because Java code sits outside the contracts that make the rest of a Nex program trustworthy.

Using Java Objects

An imported Java class is created with create, like a Nex class. A Java object is initialized via an overloaded constructor named new, which picks among the class’s constructors by the number and types of the arguments, as Java does, and the compiler reports a genuine ambiguity between two equally good constructors as an error. Once a Java object exists, its methods are called directly:

import java.lang.StringBuilder
import java.lang.System

let sb := create StringBuilder.new("Nex")
sb.append(" on the JVM")
print(sb.toString())       -- "Nex on the JVM"
print(sb.length())         -- 14

with "java" do
  print(System.getProperty("line.separator") = "\n")
end

A Java method is called by its Java name, with parentheses even when it takes no arguments: sb.length(), not sb.length.

System.getProperty(...) is different. It doesn’t call a method on an object you hold; it names the Java class System itself inside an expression. Outside a with "java" do ... end block, a name in an expression can only mean something from Nex, such as a variable, a function or a class. Inside the block, a name that matches nothing in Nex may also refer to a Java class. That’s why the call goes inside the block. create StringBuilder and sb.append(...) need no block, because StringBuilder there is a type, which import makes available everywhere, and sb is an ordinary Nex variable. The block also marks its code as host-specific: an implementation of Nex on another host would skip any with "java" block without error. Since the JVM is the only host today, what matters in practice is the naming rule.

A Java method can return null, which arrives in Nex as nil. Give such a result a detachable type and check it before use:

import java.lang.System

with "java" do
  let home: ?String := System.getProperty("app.home")
  if home = nil then
    print("app.home is not set")
  else
    print("app.home is " + home)
  end
end

Java does not say which of its methods may return null, so Nex cannot check this for you. Assigning the same result to a plain String is accepted, and the program fails only later, wherever the value is used, with Used a value that is void (nil). When the Java documentation says a method may return null, use ?Type.

The pattern: keep with blocks small. Wrap the lines that name a Java class in an expression, and nothing more, so the host-specific lines stand out.

Keeping the Boundary Small

Java objects are easy to use, and that is the risk. A program that calls StringBuilder wherever it needs one ends up with Java scattered through code that should be about its own problem. Every one of those places depends on Java’s names and behaviour, and none of them has a contract.

The better design is to wrap the Java type in one small Nex class, give that class ordinary Nex features with contracts, and let nothing else use the Java type:

import java.lang.StringBuilder

class Line_Buffer
create
  make
  do
    builder := create StringBuilder
  end
feature
  text: String
  do
    result := builder.toString()
  end

  append_line(s: String)
  do
    builder.append(s)
    builder.append("\n")
  ensure
    grew: text.length = old text.length + s.length + 1
  end
private feature
  builder: StringBuilder
end

let buf := create Line_Buffer.make
buf.append_line("Hello, Ada")
buf.append_line("Welcome to Nex on the JVM.")
print(buf.text)

The field builder has the Java type StringBuilder, so its calls are checked like any other, and it sits in a private feature section, so no other class can reach it. Callers see only append_line and text, and the postcondition grew says exactly what append_line does, in Nex terms. If Line_Buffer later stored its lines in a Nex Array instead, no caller would notice.

The wrapper is also where Java’s failures should stop. A Java exception reaches Nex code as a Nex exception. Some become Nex’s own classes: charAt(10) on a three-character StringBuilder raises an Index_Out_Of_Bounds. The rest arrive as a Host_Exception, such as getFirst() on an empty java.util.LinkedList, whose message is java.util.NoSuchElementException. Don’t let either kind leak past the wrapper. Where a precondition can rule the failure out, write one, as a queue wrapper’s first would require not is_empty. Where it cannot, catch the exception in rescue and raise the program’s own exception class instead (Chapter 21). Either way, callers depend on the wrapper’s contract, never on Java’s exception names.

Keeping the boundary small also keeps the rest of the program easy to test. Code that only computes or formats should take and return plain Nex values and never touch the wrapper, so it can be tested with ordinary strings and numbers, with no Java involved.

Implementing a Java Interface

Sometimes the direction is reversed, and a Java API needs to call your code. Java APIs ask for this through interfaces. A Thread runs a Runnable, a sort uses a Comparator, and a Swing button notifies an ActionListener. A Nex class can inherit an imported Java interface and become a real implementation of it.

The class must define a method for every abstract member of the interface, spelled exactly as Java spells it: doClick, not do_Click or do_click. Nex does not translate between its own naming style and Java’s.

import java.lang.Runnable
import java.lang.Thread

class Countdown inherit Runnable
create
  make(n: Integer)
  require
    non_negative: n >= 0
  do
    start_at := n
  end
feature
  start_at: Integer

  run
  do
    count_down()
  end

  count_down
  do
    from
      let i := start_at
    until
      i = 0
    do
      print(i)
      i := i - 1
    end
    print("liftoff")
  end
end

let t := create Thread.new(create Countdown.make(3))
t.start()
t.join()
3
2
1
"liftoff"

Countdown is a genuine java.lang.Runnable. Thread calls its run method exactly as it would call one written in Java. This works the same on the interpreter and the compiled backend.

The pattern: keep the interface method a thin adapter. run does nothing but call count_down, an ordinary Nex feature that can be tested and given contracts without starting a thread. The Java-facing name is a doorway into Nex code, not the place where the work happens.

Extending a Java Class

A Nex class can also inherit a concrete Java class and become a real subclass of it at the bytecode level. This is a heavier commitment than implementing an interface, and it has three rules:

  • it works only on the compiled backend; the interpreter reports a clear error instead
  • a class can extend at most one Java class, as in Java, though it can also implement any number of Java interfaces and inherit Nex classes
  • a constructor that needs the Java superclass’s constructor calls super.new(…) as its first statement, because the JVM requires the superclass to be set up before anything else touches the object
import java.lang.Thread

class Named_Worker inherit Thread
create
  make(label: String)
  do
    super.new(label)
  end
feature
  run
  do
    print("running " + this.getName())
  end
end

let w := create Named_Worker.make("indexer")
w.start()
w.join()
"running indexer"

super.new(label) runs Thread’s constructor that takes a name. run overrides Thread’s own run, so start calls this version on the new thread. And start, join and getName are inherited from Thread, never declared by Named_Worker. Inside the class, an inherited Java method is called through this, as in this.getName(). Without it, getName() is reported as undefined. A subclass that declares no constructor of its own relies on the Java class’s public constructor with no arguments.

The pattern: prefer implementing an interface to extending a class. Countdown and Named_Worker both end up running on a thread, but Countdown stays an ordinary Nex class that merely also implements Runnable. Named_Worker is a Thread, with every public method of Thread in its interface, and it cannot run on the interpreter. Extend a Java class only when an API leaves no choice, because it asks for a subclass and offers no interface.

Adding Features to a Java Class

Inheriting a Java class makes a new class. Sometimes what you want instead is to give an existing Java class a feature of your own, so that every StringBuilder has it, wherever it was made. An extend block (Chapter 23) does that for Java classes and interfaces just as it does for Nex classes:

import java.lang.StringBuilder
import java.util.LinkedList
import java.util.List

extend StringBuilder
feature
  is_blank: Boolean
  do
    result := length() = 0
  end

  add_line(s: String)
  do
    append(s)
    append("\n")
  end
end

extend List
feature
  describe: String
  do
    result := "a list of " + size().to_string
  end
end

let sb: StringBuilder := create StringBuilder
print(sb.is_blank)       -- true
sb.add_line("first")
print(sb.is_blank)       -- false

let names: LinkedList := create LinkedList
names.add("Ada")
names.add("Bo")
print(names.describe)    -- "a list of 2"

In the body, this is the Java object, and the class’s own methods can be called without it, as length() and append are here. An interface can be extended too: LinkedList implements List, so it has describe. This works the same on the interpreter and the compiled path, outside with "java" blocks as well as inside them.

A few rules keep this predictable:

  • the Java class must be imported, and the extension takes no generic parameters
  • a feature cannot have the name and number of arguments of one of the Java class’s public methods, so it never hides one
  • a feature can be added to only one class of a Java hierarchy: adding describe to both List and LinkedList is an error, and LinkedList gets List’s anyway
  • the Java classes that hold Nex’s own values, such as ArrayList (Nex’s Array) and String, cannot be extended, since that would change the Nex type too; the error says which Nex type to extend instead

The pattern here is a choice between two designs. Wrap a Java type when the rest of the program should not know it exists, as Line_Buffer hides StringBuilder. Extend it when the program already passes the Java type around and only needs a convenience on it. In that case keep each extension short, give it a contract, and keep it in one module, rather than repeating raw Java calls through the program.

Summary

  • import brings in host-platform symbols; intern brings in Nex classes
  • Keep interop code near system boundaries rather than scattering it through core logic
  • Create Java objects with create, passing constructor arguments to new, and call their methods directly; only code that names a Java class in an expression, such as System.getProperty(...), needs a with "java" block
  • Wrap a Java type in one small Nex class with contracts, so the rest of the program never sees it
  • inherit an imported Java interface to implement it, with methods named exactly as Java names them, and keep those methods thin adapters over ordinary Nex features. This works on both the interpreter and the compiled path
  • inherit a concrete Java class to extend it, forwarding to its constructor with super.new(...). This works on the compiled backend only, so prefer implementing an interface when the API allows it
  • extend an imported Java class or interface to give every instance a feature of your own, on both the interpreter and the compiled path
  • A Java method may return null: give its result a ?Type
  • Java exceptions arrive as Nex exceptions, either built-in classes or Host_Exception; a wrapper should rule them out with preconditions or translate them, so they never reach its callers
  • Portable core logic is easier to test, reason about, and reuse

Exercises

1. Write a short example containing both an intern statement and an import statement. Explain the different role each plays.

2. Choose a small program idea and identify which parts should remain pure Nex logic and which parts belong to the host boundary.

3. Write a wrapper-class design for a clock or random-number service. State the contract of the main routine and explain what remains host-specific.

4. Explain when disabling runtime contract checks in a production build might be reasonable, and when it is risky.

5. Extend java.lang.StringBuilder with a command add_all(lines: Array[String]) that appends each line followed by a newline. Then try to add a feature named reverse and read the error.

6.* Take one earlier example, such as a report printer or configuration loader, and redesign it so that host-specific work is isolated in one class while the main computation remains platform-independent.
