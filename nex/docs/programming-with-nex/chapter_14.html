Chapter 14

Inheritance and Polymorphism

In the last chapter we established that a class should model one concept well. Sometimes concepts form families. A rook and a knight are both chess pieces: each belongs to a side, white or black, and each stands on a square of the board, but each moves by its own rule. Members of a family share common behaviour while differing in specifics. Inheritance is the mechanism for expressing that relationship in code.

What Inheritance Is

Inheritance allows one class — the subclass — to extend another — the superclass. The subclass inherits all the fields and methods of the superclass and can add new ones or override existing ones.

The relationship is is-a: a Rook is a Piece. This is not just a programming convenience — it reflects a genuine conceptual relationship. If the is-a relationship does not hold, inheritance is probably the wrong tool.

In Nex, inheritance is declared with inherit. A move is described by how far a piece travels: dx squares sideways and dy squares up the board.

nex> class Piece
     create
       make(s: String) do
         side := s
       end
     feature
       side: String
       name: String do result := "piece" end
       can_move(dx, dy: Integer): Boolean do result := false end
       describe: String do
         result := side + " " + name
       end
     end

nex> class Rook inherit Piece
     create
       make(s: String) do
         Piece.make(s)
       end
     feature
       name: String do result := "rook" end
       can_move(dx, dy: Integer): Boolean do
         result := (dx = 0) /= (dy = 0)
       end
     end

nex> class Pawn inherit Piece
     create
       make(s: String) do
         Piece.make(s)
         direction := when s = "white" then 1 else -1 end
       end
     feature
       direction: Integer
       name: String do result := "pawn" end
       can_move(dx, dy: Integer): Boolean do
         result := dx = 0 and dy = direction
       end
     end

Both Rook and Pawn inherit the side field and the describe method from Piece. Each overrides name and can_move with its own version. A rook moves along a row or a column: exactly one of dx and dy is zero, which is what (dx = 0) /= (dy = 0) says. A pawn moves one square straight ahead, and "ahead" depends on its side, so Pawn adds a field of its own, direction: up the board for white, down for black.

Public class constants are inherited as well. If a parent class defines:

class Piece
feature
  BOARD_SIZE = 8
end

then child classes may use BOARD_SIZE directly inside their own features, and external code may still refer to it with a class name such as Piece.BOARD_SIZE.

This is useful for shared limits, default labels, configuration values, and other facts that belong to the class definition rather than to each object.

Superclass Calls

When a subclass constructor runs, it must also initialise the fields inherited from the superclass. Naming the superclass explicitly delegates to its constructor:

make(s: String) do
  Piece.make(s)                                      -- initialises side in Piece
  direction := when s = "white" then 1 else -1 end   -- initialises direction in Pawn
end

Piece.make(s) runs Piece’s make constructor, setting side := s. Then the Pawn constructor sets direction. Both fields are properly initialised.

When a class inherits from exactly one parent — the usual case — the keyword super says the same thing without naming it:

make(s: String) do
  super.make(s)   -- same as Piece.make(s)
  direction := when s = "white" then 1 else -1 end
end

super resolves to whichever class Pawn inherits from, so the call still reads correctly if Piece is later renamed. This only works because Pawn has a single parent — a class declared with inherit A, B has two, and super would have no way to choose between them, so it is rejected at compile time there; the one you mean must be named explicitly, as above.

super can call an overridden superclass method from within an override the same way. Suppose a pawn should also say which way it is heading:

describe: String do
  result := super.describe + " moving " + when direction = 1 then "up" else "down" end
end

A black pawn with this describe calls itself "black pawn moving down". The method builds on Piece’s describe rather than duplicating it — and, as with the constructor, Piece.describe would do exactly the same thing here, since Pawn has only the one parent. Reach for the explicit form when you need to be precise about which ancestor you mean, or when super alone would be ambiguous; otherwise super is the more direct way to say “my superclass’s version of this.”

Overriding Methods

When a subclass defines a feature with the same name as a superclass feature, the subclass version overrides it. Calling can_move on a Rook runs Rook’s version, not Piece’s; describe, which Rook does not override, runs Piece’s version, and that in turn calls Rook’s name:

nex> let r := create Rook.make("white")
nex> r.describe
"white rook"

nex> r.can_move(0, 3)
true

nex> r.can_move(1, 2)
false

When you override a method, its signature may change in only one safe direction. The overriding version may widen a parameter — accept a more general type than the inherited method did — and may narrow the return type — promise a more specific result. It may not do the reverse. The rule has a name: parameters are contravariant and the return type is covariant.

The reason is substitutability. Because a Rook can be used wherever a Piece is expected, anyone holding one as a Piece may call its methods in the way Piece allows. If a subclass redefined a method to demand a narrower argument than the superclass promised to accept, such a call could hand the override a value it cannot handle. Nex rejects that at compile time, naming the method and the offending parameter. When you really do want a subclass method to treat one subtype specially, keep the wider parameter type and narrow inside the body with convert or match.

Polymorphism

The most powerful consequence of inheritance is polymorphism: the ability to treat objects of different subclasses through a common superclass type.

Add one more kind of piece. A knight jumps in an L: two squares one way and one square the other, so the product of the two distances is always 2:

nex> class Knight inherit Piece
     create
       make(s: String) do
         Piece.make(s)
       end
     feature
       name: String do result := "knight" end
       can_move(dx, dy: Integer): Boolean do
         result := dx.abs * dy.abs = 2
       end
     end

An Array[Piece] can hold rooks, knights, pawns, or any other piece subclass:

nex> let pieces: Array[Piece] := []
nex> pieces.add(create Rook.make("white"))
nex> pieces.add(create Knight.make("black"))
nex> pieces.add(create Pawn.make("black"))

nex> across pieces as p do
       print(p.describe)
     end
"white rook"
"black knight"
"black pawn"

When p.describe is called, it calls name, and Nex dispatches to the correct name for the actual runtime type of each object. This is dynamic dispatch: the method called is determined by the object’s type at runtime, not by the declared type of the variable.

The same holds for can_move. Which pieces can make a given move? Ask each of them, without knowing or caring what kind it is:

nex> pieces.filter(fn (p) => p.can_move(1, 2)).map(fn (p) => p.describe)
["black knight"]

nex> pieces.filter(fn (p) => p.can_move(0, -1)).map(fn (p) => p.describe)
["white rook", "black pawn"]

Polymorphism means code written against the superclass type works correctly with any subclass — including subclasses not yet written. Adding a Bishop that inherits Piece and overrides name and can_move would work with the code above without changing it.

This idea is closely related to the Liskov Substitution Principle: if a routine expects a Piece, it should be able to work with a Rook or a Knight without needing special-case knowledge. In practical terms, a subclass should behave like a valid, more specific version of its superclass. It may extend behaviour, but it should not violate the expectations established by the parent type.

When Inheritance Is the Right Tool

Inheritance is appropriate when:

The is-a relationship is genuine. A Knight is a Piece. A Pawn is a Piece. The subclass is a more specific version of the superclass concept.

The subclass shares and specialises superclass behaviour. It uses the inherited methods and overrides some to provide specialised behaviour. It does not ignore or neutralise what it inherits.

You need polymorphism. You want to write code against the superclass type and have it work correctly on any subclass instance.

Inheritance is not appropriate when:

The relationship is has-a, not is-a. A Board has pieces — it does not extend Piece. Using inheritance to share code between conceptually unrelated classes produces fragile designs.

You only want to reuse code. If the goal is to avoid duplicating a few methods, composition — giving a class a field of another class type and delegating to its methods — is usually better. The queen is the classic trap. A queen moves like a rook or like a bishop, so it is tempting to write class Queen inherit Rook, Bishop and get both movement rules for free. But a queen is not a rook: every routine that expects a Rook would now accept a queen, and every change to Rook would silently change the queen. A Queen is a Piece, and its can_move should say what a queen does — the rook's rule or the bishop's — whether it spells the rules out or borrows them from a helper both classes share.

The subclass needs to override most of what it inherits. A subclass that overrides everything is not a specialisation — it is a different class wearing a misleading name.

Feature Override

A superclass can provide a default implementation for a method that subclasses override with specialised behaviour. This is useful when the superclass defines a general structure and the subclass fills in the details.

Every move must stay on the board, whatever the piece. That part of the rule is the same for every piece, so it belongs in Piece. Which moves a piece can make at all is different for each kind, so Piece only provides a safe default for it:

nex> class Piece
     create
       make(s: String) do
         side := s
       end
     feature
       BOARD_SIZE = 8
       side: String
       name: String do result := "piece" end
       can_move(dx, dy: Integer): Boolean do result := false end
       can_reach(dx, dy: Integer): Boolean do
         result := dx.abs < BOARD_SIZE and dy.abs < BOARD_SIZE and can_move(dx, dy)
       end
       describe: String do
         result := side + " " + name
       end
     end

can_move returns false by default. The can_reach method in Piece checks the board size and then calls can_move, and subclasses override can_move with their own rule:

nex> class Rook inherit Piece
     create
       make(s: String) do
         Piece.make(s)
       end
     feature
       name: String do result := "rook" end
       can_move(dx, dy: Integer): Boolean do
         result := (dx = 0) /= (dy = 0)
       end
     end

nex> let r := create Rook.make("white")
nex> r.can_reach(0, 7)
true

nex> r.can_reach(0, 9)
false

can_reach in Piece calls can_move — which runs Rook’s can_move because r is a Rook. A rook may move along a column as far as it likes, but nine squares would take it off the board. The superclass defines the structure; the subclass fills in the detail. This is the template method pattern: a superclass method calls an overridable method whose behaviour varies by subclass.

A Worked Example: Pieces on a Board

So far a piece has known only how it moves, not where it is. In this example each piece also remembers its square, as a column col and a row row, both counted from 0. Moving a piece checks the move and, if it is allowed, updates the square:

nex> class Piece
     create
       make(s: String, c, r: Integer) do
         side := s
         col := c
         row := r
       end
     feature
       BOARD_SIZE = 8
       side: String
       col: Integer
       row: Integer
       name: String do result := "piece" end
       can_move(dx, dy: Integer): Boolean do result := false end
       on_board(c, r: Integer): Boolean do
         result := c >= 0 and c < BOARD_SIZE and r >= 0 and r < BOARD_SIZE
       end
       move_to(c, r: Integer): Boolean do
         if on_board(c, r) and can_move(c - col, r - row) then
           col := c
           row := r
           result := true
         else
           result := false
         end
       end
       square: String do
         result := "abcdefgh".char_at(col).to_string + (row + 1).to_string
       end
       describe: String do
         result := side + " " + name + " on " + square
       end
     end

nex> class Knight inherit Piece
     create
       make(s: String, c, r: Integer) do
         Piece.make(s, c, r)
       end
     feature
       name: String do result := "knight" end
       can_move(dx, dy: Integer): Boolean do
         result := dx.abs * dy.abs = 2
       end
     end

nex> class Pawn inherit Piece
     create
       make(s: String, c, r: Integer) do
         Piece.make(s, c, r)
         direction := when s = "white" then 1 else -1 end
         moved := false
       end
     feature
       direction: Integer
       moved: Boolean
       name: String do result := "pawn" end
       can_move(dx, dy: Integer): Boolean do
         result := dx = 0 and (dy = direction or (not moved and dy = 2 * direction))
       end
       move_to(c, r: Integer): Boolean do
         result := Piece.move_to(c, r)
         if result then
           moved := true
         end
       end
       describe: String do
         result := Piece.describe + when moved then "" else " (not yet moved)" end
       end
     end

square names a square the way chess players do: columns are the letters a to h and rows the numbers 1 to 8, so column 6, row 0 is g1.

nex> let knight := create Knight.make("white", 6, 0)
nex> let pawn := create Pawn.make("white", 4, 1)
nex> let pieces: Array[Piece] := [knight, pawn, create Pawn.make("black", 3, 6)]
nex> across pieces as p do
       print(p.describe)
     end
"white knight on g1"
"white pawn on e2 (not yet moved)"
"black pawn on d7 (not yet moved)"

nex> knight.move_to(5, 2)    -- g1 to f3
true
nex> knight.move_to(5, 3)    -- f3 to f4: not a knight's move
false
nex> pawn.move_to(4, 3)      -- e2 to e4: two squares, allowed on a first move
true
nex> pawn.move_to(4, 5)      -- e4 to e6: two squares again
false
nex> pawn.move_to(4, 4)      -- e4 to e5
true

nex> across pieces as p do
       print(p.describe)
     end
"white knight on f3"
"white pawn on e5"
"black pawn on d7 (not yet moved)"

nex> knight.move_to(7, 3)    -- f3 to h4
true
nex> knight.move_to(8, 5)    -- h4 to "i6": a knight's move, but off the board
false

Knight inherits move_to, square and describe unchanged and supplies only its movement rule. Pawn needs more. A pawn may move two squares on its first move, so it has to remember whether it has moved, and its can_move consults that field. To keep the field up to date, Pawn overrides move_to.

Notice how it does that. Pawn does not assign col and row itself: those fields belong to Piece, and only code in Piece may assign them. Instead, Pawn.move_to calls Piece.move_to to do the actual move, then records that the pawn has moved if the move succeeded. And Piece.move_to calls can_move, which dispatches back to Pawn’s version — the template method of Section 14.6 again. Both describe overrides build on Piece.describe. The array holds all three pieces as Piece, and every call dispatches to the right class.

Deferred Classes

Sometimes a class exists to define a common interface that subclasses must fill in. The superclass itself has no meaningful implementation for certain methods — only its subclasses do. Nex captures this with the deferred modifier.

A deferred class cannot be instantiated directly. It exists to be inherited:

deferred class Piece
feature
  side: String
  set_side(s: String) do side := s end
  name: String deferred
  can_move(dx, dy: Integer): Boolean deferred
  describe: String do
    result := side + " " + name
  end
end

name and can_move are declared with the deferred keyword in place of a body. These are deferred features: the class announces what every piece can do, but leaves the how to each subclass. describe has a body and is inherited as-is; it calls name, which will dispatch to the subclass implementation at runtime.

set_side is here because Piece has no constructor of its own: side can only ever be assigned by code belonging to Piece, the class that declares it — a subclass may read side directly, exactly as describe above does, but not assign it, even from its own constructor. This is the same rule the pawn in Section 14.7 already followed when it moved through Piece.move_to: it exists to protect whatever Piece itself guarantees about side from being bypassed by a subclass writing straight to the field.

Any concrete subclass must implement all deferred features:

class Knight inherit Piece
create
  make(s: String) do
    set_side(s)
  end
feature
  name: String do result := "knight" end
  can_move(dx, dy: Integer): Boolean do
    result := dx.abs * dy.abs = 2
  end
end

nex> let k := create Knight.make("black")
nex> k.describe
"black knight"

Knight provides name and can_move, so it is concrete and can be instantiated. If it omitted either, the compiler would report an error. A subclass that does not implement all deferred features must itself be declared deferred.

Attempting to instantiate a deferred class directly is a compile-time error:

let p: Piece := create Piece.make(...)   -- error: cannot instantiate deferred class

The value of deferred is polymorphism without a misleading default. Compare it to the feature-override approach from Section 14.6: there, can_move returned false as a fallback. A new kind of piece that forgot to override it would compile, run, and silently never move. With deferred, the compiler enforces that every concrete subclass provides a real implementation. A missing override is a compile-time error, not a runtime surprise.

deferred is the right choice when:

The concept is meaningful but has no implementation at the abstract level. Every piece has a way of moving; "how a piece in general moves" has no answer.

Every subclass must override a method, and a default would be misleading or dangerous. A default can_move that always says no, a default authenticate that always returns true — these are traps. deferred removes the trap.

You want the compiler to enforce completeness. Each new subclass is checked at compile time. No subclass can slip through without satisfying the contract.

When the set of subclasses is also fixed and known, deferred can be combined with sealed to close the hierarchy entirely — that is the subject of the next section.

Sealed Classes and Closed Hierarchies

Ordinary inheritance is open: anyone can add a new subclass. Sometimes that is exactly right. Other times, a hierarchy is meant to be complete — there are exactly two kinds of result, exactly three kinds of network event — and allowing arbitrary extension would break every routine that handles them.

The sealed modifier closes a hierarchy. A sealed deferred class cannot be instantiated and cannot be extended outside the scope where it and its known subclasses are defined:

sealed deferred class Result
end

class Ok inherit Result
feature
  value: Integer
create
  make(v: Integer) do value := v end
end

class Err inherit Result
feature
  msg: String
create
  make(m: String) do msg := m end
end

Result is now a closed family: Ok and Err are the only variants that can ever exist.

The sealed hierarchy is what allows us to define the match statement. Because the typechecker knows every subclass of a sealed type, it can verify that a match covers all of them. A missing branch is a compile-time error, not a runtime surprise:

let r: Result := create Ok.make(42)

match r of
  Ok as ok then
    print(ok.value)       -- ok is typed as Ok here
  Err as err then
    print(err.msg)        -- err is typed as Err here
end

If you added a third variant — say Pending — to the hierarchy but forgot to add a Pending clause, the program would not compile. No silent missed case.

An else branch suppresses the exhaustiveness check and covers anything not matched by a preceding clause:

match r of
  Ok as ok then
    print(ok.value)
  else
    print("not ok")
end

Sealed hierarchies work well for any situation where the set of cases is fixed by design: operation results, state machine transitions, event tags, or domain types with a known, finite structure.

Unions: the concise form

A closed family whose variants are just data is common enough that writing the sealed parent and every subclass by hand becomes a chore. The union declaration is a shorthand for exactly that pattern. The whole Result hierarchy above collapses to:

union Result
  Ok(value: Integer)
  Err(msg: String)
end

This is not a new kind of type — it expands to the same sealed deferred class Result with an Ok and an Err subclass, each with the listed fields and a matching make constructor. Construction and match are identical to before: create Ok.make(42) builds an Ok, and a match over a Result is still checked for exhaustiveness. A variant with no data is written as a bare name. Here is a union for the moves a player can make in a turn: step a piece by some distance, castle on one side or the other, or resign:

union Move
  Step(dx: Integer, dy: Integer)
  Castle(king_side: Boolean)
  Resign
end

A variant with no data has nothing to initialise, so, like any class without fields, it gets no constructor and is created with a plain create Resign. A variant with data names its constructor and passes the data, as in create Step.make(0, 2).

Because a union only declares data, it synthesises no methods, invariants, or contracts. When a variant needs any of these, write it in the full sealed deferred class form — the two forms describe the same kind of hierarchy, and you can mix them as a design grows.

Enumerations

A special case is worth its own word. When every variant is a bare tag with no data — the days of the week, the suits of a deck, or the two sides in a game of chess — you have an enumeration: a small, fixed set of named values. Prefix the declaration with enum and Nex treats it as one:

enum union Side
  White
  Black
end

This is still the same sealed hierarchy underneath, so match and its exhaustiveness check work exactly as above. The enum keyword adds three conveniences you would otherwise write by hand:

print(Side.White == Side.White)    -- true: Side.White is one canonical value
print(Side.White < Side.Black)     -- true: members order by how they are written
print(Side.values.length())        -- 2: an array of every member, in order
across Side.values as s do
  print(s.ordinal)                 -- 0, then 1
end

Each member is a constant on the type — Side.White is the White, not a fresh object every time you name it, which is why comparing two of them with == is true. The members are ordered by their declaration order, so a Side is Comparable without your writing a compare. And Side.values gives you the whole set to loop over.

The pieces in this chapter kept their side in a String, so nothing stopped a typo like "whte", and a pawn created with it would quietly march down the board. Declared as side: Side, the field can only ever hold Side.White or Side.Black.

The enum form asks for all of this deliberately: a plain union, even one whose variants happen to be data-free, stays a bare sum type with none of these extras. enum is allowed only when no variant carries a payload and the union is not generic — its members are fixed values, which need a concrete type — and no variant may be named ordinal, compare, or values, since those name the generated members.

Matching into values

Binding the whole variant with as and then reading its fields (ok.value) is fine, but a match can also take a variant apart directly. Naming the payload fields in the pattern binds them as locals of the same name:

match r of
  Ok(value)  then print(value)     -- 'value' is bound directly
  Err(msg)   then print(msg)
end

A field pattern can rename a field (Err(msg as reason) binds it to reason), ignore one with _, or constrain it to a literal or a type (Err(msg: String)). A clause may also carry an if guard — a boolean tested after the variant matches, with the destructured names in scope; when it is false, matching continues with the following clauses:

match move of
  Step(dx, dy) if dx.abs > 1 or dy.abs > 1 then print("a long move")
  Step(dx, dy)                             then print("a single step")
  Castle(king_side)                        then print("castling")
  Resign                                   then print("game over")
end

Because a guarded clause can fail after its variant matches, it does not by itself satisfy exhaustiveness: the guarded Step clause above needs the plain Step clause (or a wildcard, or else) to cover the case where the guard is false. A lone _ pattern is a catch-all, same as else.

Once Fields

A field is normally writable throughout the lifetime of an object: any method can reassign it. Sometimes that is too permissive. An identifier assigned once in the constructor and never changed afterward is a common design — think of a database primary key, or a config-file path. Nex captures this intent with the once field modifier.

class Point
feature
  once x: Integer
  once y: Integer
create
  make(px: Integer, py: Integer) do
    x := px
    y := py
  end
feature
  show do
    print(x)
    print(y)
  end
end

let p: Point := create Point.make(3, 7)
p.show   -- 3, then 7

After make returns, x and y are fixed. Any attempt to reassign them — in a method, or anywhere outside a constructor — is a compile-time error:

class Box
feature
  once value: Integer
create
  make(v: Integer) do value := v end
feature
  overwrite(v: Integer) do
    value := v     -- error: 'value' is a once field
  end
end

Multiple constructors are permitted; each may set the once field independently:

class Box
feature
  once value: Integer
create
  make(v: Integer) do value := v end
  empty do value := 0 end
end

once is weaker than a constant: a constant requires its value at the point of declaration; a once field is computed by the constructor and fixed from that moment. This makes once the right choice whenever the value is not known until the object is created.

The modifier interacts naturally with invariants. An invariant expressing that a field never changes is a runtime assertion at every method boundary; a once modifier is a structural, compile-time guarantee. Prefer the modifier when immutability is the design intent, and use the invariant to express additional value constraints on top of it.

Summary

  • class SubClass inherit SuperClass declares the relationship; the subclass inherits all fields and methods
  • An inherited field may be read directly from the subclass, but assigned only by code belonging to the class that declares it — a subclass writes it through a method the declaring class provides, such as Piece.move_to in Section 14.7, never by assigning the field itself
  • SuperClass.constructor_name( ) calls the superclass constructor from the subclass constructor; super.constructor_name( ) does the same when there is exactly one superclass
  • this.constructor_name( ) delegates to another constructor of the same class (Chapter 12) — the same idea, one level narrower
  • SuperClass.method_name( ) calls an overridden superclass method from within an override; super.method_name( ) is the equivalent shorthand with a single superclass
  • Overriding replaces a superclass method with a subclass-specific version; dynamic dispatch calls the correct version at runtime
  • Polymorphism allows objects of different subclasses to be treated through a common superclass type
  • The template method pattern: a superclass method calls an overridable method; the superclass defines structure, subclasses fill in details via override
  • Overriding methods must honour the superclass contract; preconditions should not be strengthened, postconditions should not be weakened
  • Use inheritance for genuine is-a relationships and polymorphism; use composition for has-a relationships or code reuse without a conceptual relationship
  • A deferred class cannot be instantiated; subclasses must implement all deferred features or themselves be declared deferred — the compiler enforces completeness
  • A sealed deferred class closes the hierarchy — only defined subclasses may extend it; the typechecker enforces exhaustive handling in match
  • A once field can be assigned in any constructor but never reassigned afterward — a structural, compile-time immutability guarantee

Exercises

1. Define a class Animal with a field name: String, a constructor make, and a method sound: String that returns "..." by default. Define subclasses Dog, Cat, and Cow each overriding sound. Create an Array[Animal], add one of each, and print each animal’s name and sound.

2. Add three more pieces to the hierarchy of Section 14.7. A Bishop moves any distance diagonally (dx.abs = dy.abs, and it must actually move). A King moves one square in any direction. A Queen moves like a rook or like a bishop. Write Queen without inheriting from Rook or Bishop, and explain why. Test each one with move_to, including a move that would leave the board.

3. A pawn's answer to can_move(0, 2) depends on its side and on whether it has moved: the same pawn says true before its first move and false after it. Does Pawn honour the Liskov Substitution Principle — can a pawn be used anywhere a Piece is expected without surprising the caller? To answer, first write down what Piece.can_move actually promises. Does it promise the same answer every time, or only a truthful answer about this piece right now? What would a caller that cached the answers for every piece get wrong?

4. Define a class Vehicle with fields make: String and speed: Real, and methods fuel_type: String and max_speed: Real with sensible defaults. Define Electric_Car and Petrol_Car overriding those methods. Add can_reach(distance, fuel: Real): Boolean to each — Petrol_Car uses 10 litres per 100 km; Electric_Car uses 20 kWh per 100 km.

5.* Define a Logger base class with a method log(message: String) that prints with a prefix. Define File_Logger that also appends to a log_history: String field, and Silent_Logger that discards all messages. Create an Array[Logger] with one of each and call log("test") on each. What does this demonstrate about polymorphism and swappable implementations?
