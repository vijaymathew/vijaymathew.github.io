Chapter 27

A Spreadsheet: Formulas

This chapter and the two after it build one program from start to finish: a spreadsheet that runs on the command line. It is small enough to read in full and large enough to need everything the book has covered: classes and inheritance, sealed types and match, contracts, errors, modules and tests.

A spreadsheet is also, quietly, a small programming language. Each cell holds a formula; the program has to read that formula, understand it, and compute its value from the values of other cells. This chapter builds that language. Chapter 28 builds the sheet that keeps every cell up to date, and Chapter 29 puts a command line around it.

The Project

Here is the finished program at work. Lines starting with > are what the user types:

> A1 = 120
> A2 = 80
> A3 = A1 + A2 * 2
> B1 = SUM(A1:A3)
> show
             A         B
   1    120.00    480.00
   2     80.00
   3    280.00
> A1 = 100
> show
             A         B
   1    100.00    440.00
   2     80.00
   3    260.00
> A1 = A3
Error: A1 = A3 would make A1 depend on itself
> A4 = A1 / 0
> show A4
#DIV/0!   (A4 = A1 / 0)

Three behaviours carry the whole design. Changing A1 changes A3 and B1 too, because they are computed from it. A formula that would make a cell depend on itself is refused, because no value could ever satisfy it. And a formula that cannot be computed, like a division by zero, does not stop the program: the cell simply holds an error.

The work divides along the lines of the problem, and so do the chapters:

  • Formulas (this chapter): cell names, reading formula text, and computing a formula’s value
  • The sheet (Chapter 28): which cells depend on which, refusing cycles, and recalculating
  • The command line (Chapter 29): commands, the grid display, saving and loading, and the tests

Each part is a module in the sense of Chapter 23, a file under lib/sheet/ in the project folder. This chapter writes two of them, formula.nex and evaluate.nex. The examples below are run in the REPL, started in the project folder so that intern sheet/Formula finds the file.

Cell Names

A cell is named by its column and its row: B3 is the third row of column B. Our sheet has columns A to Z and rows 1 to 99, so a name is one capital letter followed by a number from 1 to 99.

That rule will be needed everywhere: to check what the user typed, to state preconditions, to read formulas. So it is written once, as a query, and everything else refers to it:

function column_letters(): String do
  result := "ABCDEFGHIJKLMNOPQRSTUVWXYZ"
end

function is_digit(c: Char): Boolean do
  result := "0123456789".contains(c.to_string)
end

function is_letter(c: Char): Boolean do
  result := (c >= #A and c <= #Z) or (c >= #a and c <= #z)
end

-- A cell name is a column letter A-Z followed by a row number 1-99.
function is_cell_name(text: String): Boolean do
  result := false
  if text.length >= 2 and text.length <= 3 then
    let column := text.char_at(0)
    let row := text.substring(1, text.length)
    result := column >= #A and column <= #Z
              and row.all(fn (c: Char): Boolean do result := is_digit(c) end)
              and not row.starts_with("0")
  end
end

The first guard keeps char_at and substring inside the text: a name has two or three characters. Then the row must be all digits, with no leading zero, which rules out both A0 and A05.

Nex writes a character as # followed by the character, so #A and #Z are the letters. Digits are the exception: #0 is the character with code 0, not the digit zero, so is_digit asks a string of digits instead, the same trick Chapter 11 used to recognise amounts.

The other direction, from a name to its column and row and back, is where contracts start to earn their place:

function column_of(name: String): Integer
require
  valid: is_cell_name(name)
do
  result := column_letters().index_of(name.char_at(0).to_string)
ensure
  in_range: result >= 0 and result < 26
end

function row_of(name: String): Integer
require
  valid: is_cell_name(name)
do
  result := name.substring(1, name.length).to_integer
ensure
  in_range: result >= 1 and result <= 99
end

function cell_name(column, row: Integer): String
require
  column_in_range: column >= 0 and column < 26
  row_in_range: row >= 1 and row <= 99
do
  result := column_letters().char_at(column).to_string + row.to_string
ensure
  valid: is_cell_name(result)
  same_column: column_of(result) = column
  same_row: row_of(result) = row
end

Each precondition says what a valid argument is, in terms of is_cell_name, and each postcondition says what comes back. The postcondition of cell_name is the interesting one: it promises a round trip. Whatever column and row go in, the name that comes out is valid and leads back to the same column and row. Three functions that must agree with each other now check that they do, every time cell_name runs.

nex> intern sheet/Formula
nex> is_cell_name("B3")
true
nex> is_cell_name("B0")
false
nex> column_of("C7")
2
nex> row_of("C7")
7
nex> cell_name(2, 7)
"C7"
nex> cells_in_range("A1", "B2")
["A1", "A2", "B1", "B2"]
nex> cell_name(26, 1)
Error: Precondition violation: column_in_range

A range such as A1:B2 names every cell in a rectangle. Its corners may come in either order, so the function takes the smaller and larger of each coordinate, and its postcondition says how many cells a rectangle has:

-- Every cell in the rectangle with corners `first` and `last`.
function cells_in_range(first, last: String): Array[String]
require
  valid_first: is_cell_name(first)
  valid_last: is_cell_name(last)
do
  result := []
  let left := column_of(first).min(column_of(last))
  let right := column_of(first).max(column_of(last))
  let top := row_of(first).min(row_of(last))
  let bottom := row_of(first).max(row_of(last))
  from let col := left until col > right do
    from let row := top until row > bottom do
      result.add(cell_name(col, row))
      row := row + 1
    end
    col := col + 1
  end
ensure
  whole_rectangle: result.length = ((column_of(first) - column_of(last)).abs + 1)
                                   * ((row_of(first) - row_of(last)).abs + 1)
end

From Text to Tokens

A formula like A1 + 2.5*SUM(B1:B3) is, to the program, a string of characters. Reading it happens in two steps, the same two steps every programming language takes. The first cuts the text into tokens, the words of the formula: a cell name, a number, a symbol, a function name. The second, in the next section, works out how the tokens fit together.

A token is exactly one of a handful of kinds, each carrying different data, which is what a union is for (Section 14.9):

union Token
  Number_Token(value: Real)
  Cell_Token(name: String)
  Name_Token(text: String)
  Symbol(sign: Char)
  End_Of_Input
end

function describe_token(t: Token): String do
  match t of
    Number_Token(value) then result := "number " + value.to_string
    Cell_Token(name)    then result := "cell " + name
    Name_Token(text)    then result := "name " + text
    Symbol(sign)        then result := "'" + sign.to_string + "'"
    End_Of_Input        then result := "end of formula"
  end
end

End_Of_Input carries no data. It marks the end of the formula, so that the code reading tokens always has a token to look at, even after the last real one.

The Lexer reads tokens one at a time. It keeps the text and a position in it, and its invariant says that the position never leaves the text:

class Lexer
create
  make(t: String) do
    text := t
    pos := 0
  end
feature
  text: String
  pos: Integer

  at_end: Boolean do
    result := pos >= text.length
  end

  next_token: Token do
    skip_spaces
    if at_end then
      result := create End_Of_Input
    else
      let c := text.char_at(pos)
      if is_digit(c) or c = #. then
        result := read_number
      elseif is_letter(c) then
        result := read_word
      else
        pos := pos + 1
        result := create Symbol.make(c)
      end
    end
  ensure
    moved_on: pos > old pos or at_end
  end

  skip_spaces do
    from until at_end or text.char_at(pos) /= #space do
      pos := pos + 1
    end
  end

  read_number: Token
  require
    at_number: not at_end
  do
    let start := pos
    skip_digits
    if not at_end and text.char_at(pos) = #. then
      pos := pos + 1
      skip_digits
    end
    let digits := text.substring(start, pos)
    if digits = "." then
      result := create Symbol.make(#.)
    else
      result := create Number_Token.make(digits.to_real)
    end
  ensure
    moved_on: pos > old pos
  end

  skip_digits do
    from until at_end or not is_digit(text.char_at(pos)) do
      pos := pos + 1
    end
  end

  read_word: Token
  require
    at_letter: not at_end and is_letter(text.char_at(pos))
  do
    let start := pos
    from until at_end or not (is_letter(text.char_at(pos)) or is_digit(text.char_at(pos))) do
      pos := pos + 1
    end
    let word := text.substring(start, pos).to_upper
    if is_cell_name(word) then
      result := create Cell_Token.make(word)
    else
      result := create Name_Token.make(word)
    end
  ensure
    moved_on: pos > old pos
  end
invariant
  inside_text: 0 <= pos and pos <= text.length
end

Each read_ routine has a precondition saying where it may start, and next_token only calls one after looking at the character there. #space is how Nex writes the space character, since # followed by an actual space could not be seen. A word is read up to the first character that cannot continue it, then upper-cased, and is a cell token when it is a cell name and a name token otherwise: b3 becomes the cell B3, and sum becomes the name SUM.

The postcondition moved_on on next_token deserves a closer look. It says that every call either consumes some of the text or finds that there is none left. That is the promise that makes reading a whole formula terminate: a loop that calls next_token until it sees End_Of_Input cannot go round forever on the same character. Without the postcondition, that argument lives only in the programmer’s head; with it, the lexer checks its own progress on every call.

nex> let lexer := create Lexer.make("A1 + 2.5*sum(")
nex> describe_token(lexer.next_token)
"cell A1"
nex> describe_token(lexer.next_token)
"'+'"
nex> describe_token(lexer.next_token)
"number 2.5"
nex> describe_token(lexer.next_token)
"'*'"
nex> describe_token(lexer.next_token)
"name SUM"
nex> describe_token(lexer.next_token)
"'('"
nex> describe_token(lexer.next_token)
"end of formula"
nex> lexer.pos
13

After the last real token, pos stands at 13, the length of the text: the edge that the invariant allows, but never past it.

A Grammar and a Parser

Tokens say what the words are, not what they mean together. In 1 + 2 * 3, the multiplication happens first, so the formula means 1 + (2 * 3), not (1 + 2) * 3. The rules for how tokens combine are the formula language’s grammar, and they are short enough to write down in full:

expression ::= term { ("+" | "-") term }
term       ::= factor { ("*" | "/") factor }
factor     ::= number | cell | "-" factor | "(" expression ")"
             | name "(" cell ":" cell ")"

Read ::= as “is”, | as “or”, and braces as “any number of times”. An expression is terms joined by + and -; a term is factors joined by * and /; a factor is a single number, a cell, a negated factor, a whole expression in parentheses, or a function applied to a range. Precedence falls out of the layering: because a term is built from factors before any + is considered, multiplication binds more tightly than addition.

What the parser produces is a tree, and the tree is another union. Each variant is one kind of formula, and the variants that contain smaller formulas hold them as Expr values in turn:

union Expr
  Number(value: Real)
  Ref(name: String)
  Negate(operand: Expr)
  Binary(op: Char, left: Expr, right: Expr)
  Aggregate(fn_name: String, first: String, last: String)
end

function is_function_name(name: String): Boolean do
  result := ["SUM", "MIN", "MAX", "AVERAGE"].contains(name)
end

1 + 2 * 3 becomes a Binary whose operator is +, whose left side is Number(1.0), and whose right side is another Binary for 2 * 3. The tree records the grouping that the text only implies.

The grammar translates into code almost word for word. This style is called recursive descent: one routine for each rule, each calling the routines for the rules it mentions, and factor calling back up to expression for parentheses. The parser keeps the list of tokens and the position of the current one:

class Parser
create
  make(text: String) do
    let lexer := create Lexer.make(text)
    tokens := []
    from let done := false until done do
      let t := lexer.next_token
      tokens.add(t)
      match t of
        End_Of_Input then done := true
        _            then done := false
      end
    end
    index := 0
  end
feature
  tokens: Array[Token]
  index: Integer

  current: Token do
    result := tokens.get(index)
  end

  at_end: Boolean do
    match current of
      End_Of_Input then result := true
      _            then result := false
    end
  end

  at_symbol(c: Char): Boolean do
    match current of
      Symbol(sign) then result := sign = c
      _            then result := false
    end
  end

  advance
  require
    not_at_end: not at_end
  do
    index := index + 1
  ensure
    moved_on: index = old index + 1
  end

  expect(c: Char) do
    if at_symbol(c) then
      advance
    else
      raise "expected '" + c.to_string + "' but found " + describe_token(current)
    end
  end

  formula: Expr do
    result := expression
    if not at_end then
      raise "unexpected " + describe_token(current)
    end
  ensure
    all_read: at_end
  end

  expression: Expr do
    result := term
    from until not (at_symbol(#+) or at_symbol(#-)) do
      let op := when at_symbol(#+) then #+ else #- end
      advance
      result := create Binary.make(op, result, term)
    end
  end

  term: Expr do
    result := factor
    from until not (at_symbol(#*) or at_symbol(#/)) do
      let op := when at_symbol(#*) then #* else #/ end
      advance
      result := create Binary.make(op, result, factor)
    end
  end

  factor: Expr do
    match current of
      Number_Token(value) then
        do
          advance
          result := create Number.make(value)
        end
      Cell_Token(name) then
        do
          advance
          result := create Ref.make(name)
        end
      Name_Token(text) then result := call(text)
      Symbol(sign) if sign = #- then
        do
          advance
          result := create Negate.make(factor)
        end
      Symbol(sign) if sign = #( then
        do
          advance
          result := expression
          expect(#))
        end
      _ then raise "unexpected " + describe_token(current)
    end
  end

  call(name: String): Expr do
    if not is_function_name(name) then
      raise "unknown function " + name
    end
    advance
    expect(#()
    let first := cell
    expect(#:)
    let last := cell
    expect(#))
    result := create Aggregate.make(name, first, last)
  end

  cell: String do
    match current of
      Cell_Token(name) then
        do
          advance
          result := name
        end
      _ then raise "expected a cell but found " + describe_token(current)
    end
  end
invariant
  never_empty: tokens.length > 0
  inside_tokens: 0 <= index and index < tokens.length
end

Compare expression and term with their rules: each reads one operand, then, as long as the current token is one of its operators, reads another and combines the two into a Binary. Building the result from the left is what makes 8 - 2 - 1 mean (8 - 2) - 1, which is 5, rather than 8 - (2 - 1).

The contracts mark the edges the parser must not cross. The invariant keeps index on a real token. The precondition of advance, not_at_end, forbids stepping past End_Of_Input; since every token the parser advances over has first been examined, and End_Of_Input is never accepted as an operand, no correct parser ever violates it. If one did, the bug would be reported at the step that went too far, not as a confusing failure somewhere later. The postcondition of formula, all_read, records that the whole formula was used: 1 2 is not the formula 1 with something left over.

Errors at the Boundary

A user will type formulas that are not formulas. That is not a bug in the program, so it must not be a contract violation; it is an ordinary outcome that the program must handle. Chapter 21 drew exactly this line, and Chapter 22 recommended a Result wherever a caller is expected to deal with failure routinely.

Inside the parser, though, an exception is the convenient tool. A syntax error can be discovered five calls deep in factor, and raise carries it straight out without every routine in between having to check and pass it along. So the parser raises, and one function at the boundary turns the outcome into a Result:

-- What the user typed, and the tree it means.
class Formula
create
  make(t: String, e: Expr) do
    text := t
    expr := e
  end
feature
  text: String
  expr: Expr
end
-- The tree for `text`, or why it is not a formula.
function parse_formula(text: String): Result[Formula, String] do
  let parser := create Parser.make(text)
  result := create Ok[Formula, String].make(create Formula.make(text.trim, parser.formula))
rescue
  result := create Err[Formula, String].make(exception.to_string)
end

A Formula keeps the text the user typed together with the tree it means: the tree is what the program computes with, and the text is what it shows back and saves. parse_formula uses the standard Result type from data/Result (Chapter 22). Callers outside this module never see an exception from parsing; they see an Ok holding a formula or an Err holding a message:

nex> intern sheet/Evaluate
nex> function try_formula(text: String): String do
       match parse_formula(text) of
         Ok as ok then result := "ok: " + ok.value.text
         Err as e then result := "error: " + e.error
       end
     end
nex> try_formula(" a1 + A2*2 ")
"ok: a1 + A2*2"
nex> try_formula("(1 + 2")
"error: expected ')' but found end of formula"
nex> try_formula("1 2")
"error: unexpected number 2.0"
nex> try_formula("SUM(A1)")
"error: expected ':' but found ')'"
nex> try_formula("COUNT(A1:A3)")
"error: unknown function COUNT"
nex> try_formula("A1 $ 2")
"error: unexpected '$'"

Values, Including Wrong Ones

A formula can be perfectly well formed and still have no sensible value. A1 / A2 is a fine formula until A2 is zero. A spreadsheet does not refuse the formula and does not crash: it shows an error in the cell, and any cell computed from that one shows the error too.

So a value is either a number or the reason there is no number, and once more a union says exactly that:

-- A cell's value: a number, or the reason it could not be computed.
union Value
  Num(amount: Real)
  Failed(code: String)
end

function show_value(v: Value): String do
  match v of
    Num(amount)  then result := amount.format(2)
    Failed(code) then result := code
  end
end

Treating errors as values, rather than raising them, is a deliberate choice. An exception would stop the whole recalculation at the first bad cell, and the user would see nothing at all. A Failed value is just another value: it is stored in its cell, displayed in the grid, and passed on to whatever reads it.

Real arithmetic does not give us this for free. Dividing a Real by zero does not raise in Nex; it produces infinity:

nex> 120.0 / 0.0
Infinity

A spreadsheet that showed Infinity would be hiding the user’s mistake behind a number. So division checks for zero itself, and the combining routine passes a failed operand straight through:

function negate(v: Value): Value do
  match v of
    Num(amount)  then result := create Num.make(-amount)
    Failed       then result := v
  end
end

function combine(op: Char, a, b: Value): Value
require
  known_operator: "+-*/".contains(op.to_string)
do
  match a of
    Failed then result := a
    Num(amount as x) then
      match b of
        Failed then result := b
        Num(amount as y) then result := arithmetic(op, x, y)
      end
  end
end

function arithmetic(op: Char, x, y: Real): Value
require
  known_operator: "+-*/".contains(op.to_string)
do
  if op = #+ then
    result := create Num.make(x + y)
  elseif op = #- then
    result := create Num.make(x - y)
  elseif op = #* then
    result := create Num.make(x * y)
  elseif y = 0.0 then
    result := create Failed.make("#DIV/0!")
  else
    result := create Num.make(x / y)
  end
end

The precondition known_operator says which operators exist. The parser only ever builds those four, so the precondition documents a promise between the parser and the evaluator, and would catch the day someone added an operator to one and forgot the other.

Evaluating Against an Abstraction

To compute A1 + A2 * 2, the evaluator needs the values of A1 and A2. The obvious design passes it the sheet. But the sheet does not exist yet, and when it does, it will be a large object with its own concerns: storing cells, tracking dependencies, recalculating. The evaluator needs exactly one thing from it: the value of a cell, given its name.

So the evaluator asks for exactly that, through a deferred class (Section 14.8):

-- Anything formulas can read cell values from.
deferred class Cell_Source
feature
  value_of(name: String): Value
  require
    valid_name: is_cell_name(name)
  deferred
end

This is the dependency inversion principle: the evaluator, the higher-level logic, depends on a small abstraction that it defines itself, and the sheet will be one implementation of it. The evaluator does not know the sheet exists. That makes it simpler to read, and, as the next section shows, easy to test on its own.

The precondition belongs to the abstraction and is inherited by every implementation (Section 20.9): whatever supplies cell values may assume it is asked only about real cell names.

Evaluation itself is one match over the tree, with a clause for each kind of formula:

function evaluate(e: Expr, cells: Cell_Source): Value do
  match e of
    Number(value)              then result := create Num.make(value)
    Ref(name)                  then result := cells.value_of(name)
    Negate(operand)            then result := negate(evaluate(operand, cells))
    Binary(op, left, right)    then result := combine(op, evaluate(left, cells), evaluate(right, cells))
    Aggregate(fn_name, first, last) then
      result := aggregate(fn_name, cells_in_range(first, last).map(fn (n: String): Value do
        result := cells.value_of(n)
      end))
  end
end

A function applied to a range evaluates every cell in the range and hands the values to aggregate, which computes the sum, minimum, maximum or average, or returns the first failure among them:

function aggregate(fn_name: String, values: Array[Value]): Value
require
  known_function: is_function_name(fn_name)
  some_values: values.length > 0
do
  result := create Num.make(0.0)
  let amounts: Array[Real] := []
  across values as v do
    match v of
      Num(amount) then amounts.add(amount)
      Failed      then result := v
    end
  end
  if amounts.length = values.length then
    let total := amounts.fold(0.0, fn (acc, x: Real): Real do result := acc + x end)
    if fn_name = "SUM" then
      result := create Num.make(total)
    elseif fn_name = "AVERAGE" then
      result := create Num.make(total / amounts.length.to_real)
    elseif fn_name = "MIN" then
      result := create Num.make(amounts.fold(amounts.get(0), fn (acc, x: Real): Real do result := acc.min(x) end))
    else
      result := create Num.make(amounts.fold(amounts.get(0), fn (acc, x: Real): Real do result := acc.max(x) end))
    end
  end
end

The sheet will also need to know which cells a formula reads, to keep track of dependencies. That is another walk over the same tree:

-- The cells a formula reads.
function references(e: Expr): Array[String] do
  match e of
    Number                     then result := []
    Ref(name)                  then result := [name]
    Negate(operand)            then result := references(operand)
    Binary(op, left, right)    then result := references(left).concat(references(right))
    Aggregate(fn_name, first, last) then result := cells_in_range(first, last)
  end
ensure
  all_cells: result.all(fn (n: String): Boolean do result := is_cell_name(n) end)
end

Chapter 23 described the trade-off this code is making. A family of classes can grow in two directions: new variants, or new operations on all of them. Here the variants are fixed by the grammar, and the operations keep coming: evaluate, references, and in the exercises, printing a formula back as text. With a match, each new operation is one new function in one place, and the compiler checks that it handles every kind of formula. Had each variant carried its own evaluate method instead, each new operation would mean editing all five classes.

Testing Without a Sheet

Because the evaluator asks only for a Cell_Source, it can be tested before the sheet is written, against a stand-in whose values are fixed in a map. A cell missing from the map reads as zero, as an empty cell will:

nex> class Fixed_Cells inherit Cell_Source
     create
       make(m: Map[String, Real]) do
         values := m
       end
     feature
       values: Map[String, Real]
       value_of(name: String): Value do
         result := create Num.make(values.try_get(name, 0.0))
       end
     end
nex> function value_text(text: String, cells: Cell_Source): String do
       match parse_formula(text) of
         Ok as ok then result := show_value(evaluate(ok.value.expr, cells))
         Err as e then result := "error: " + e.error
       end
     end
nex> let cells := create Fixed_Cells.make({"A1": 120.0, "A2": 80.0})
nex> value_text("A1 + A2 * 2", cells)
"280.00"
nex> value_text("SUM(A1:A3)", cells)
"200.00"
nex> value_text("AVERAGE(A1:A2)", cells)
"100.00"
nex> value_text("-A1 + C9", cells)
"-120.00"
nex> value_text("A1 / (A2 - 80)", cells)
"#DIV/0!"
nex> value_text("1 + A1 / 0", cells)
"#DIV/0!"

Fixed_Cells is a fake: a real implementation of the abstraction, written for testing, with no behaviour beyond what the test needs. The last two results show errors behaving as values: a division by zero fails, and a formula that adds to the failure fails in turn, without anything raising.

The formula language is now complete: it reads text, reports mistakes, and computes values, and it knows nothing about where those values are stored. The next chapter gives it somewhere to store them.

Summary

  • A rule needed in many places, like what a cell name is, belongs in one query that the rest of the program, and its contracts, refer to
  • A postcondition can tie several routines together: cell_name promises a round trip through column_of and row_of
  • Reading a language takes two steps: a lexer cuts text into tokens, and a parser fits tokens into a tree
  • A progress postcondition, like the lexer’s moved_on, is the argument that a loop terminates, checked on every call
  • Recursive descent turns each grammar rule into one routine; precedence comes from the layering of the rules
  • Inside a module, an exception is a convenient way out; at the module’s boundary, a Result tells callers that failure is an expected outcome
  • Errors that the user should see belong in the data, as values, not in the control flow
  • Depending on a small abstraction rather than a large concrete class keeps code simple and makes it testable with a fake

Exercises

1. The lexer upper-cases words, so b3 in a formula means B3, but is_cell_name("b3") is false. Is that inconsistent? Decide where case should be normalised in the program, and why only one place should do it.

2. Write formula_text(e: Expr): String, which turns a tree back into text with every binary operation in parentheses: 1 + 2 * 3 becomes (1.0 + (2.0 * 3.0)). Use it to check that 8 - 2 - 1 is grouped from the left.

3. Write constant_value(e: Expr): ?Real, which returns the value of a formula that reads no cells, and nil for one that does. Which existing function makes the check a single line?

4. Explain the precondition not_at_end on Parser.advance. Which token would the parser reach if it advanced past End_Of_Input, and why is a precondition better here than an if inside advance that quietly does nothing?

5. Add a power operator ^ that binds more tightly than *, so that 2 * 3 ^ 2 is 18. Write the new grammar rule, say which parser routine changes, and find every contract in the two modules that must change with it.

6. aggregate returns the first failure in a range. A real spreadsheet’s SUM also skips cells that hold text. Our cells hold only numbers and errors, but suppose a future version adds text. Would you change Value, aggregate, or both? What would the postcondition of references have to say then?

7.* Rewrite evaluation the other way: give each variant of Expr its own evaluate method, using a sealed deferred class instead of a union. Then add formula_text from Exercise 2 to both versions, and compare how many places each one makes you edit.
