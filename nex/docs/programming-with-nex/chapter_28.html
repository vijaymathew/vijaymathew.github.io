Chapter 28

A Spreadsheet: The Sheet

Chapter 27 built a formula language that can compute a value from any Cell_Source. This chapter builds the sheet: the object that holds every cell’s formula and value, keeps the values current when a formula changes, and refuses any formula that would make a cell depend on itself.

The sheet is where the program’s most important promises live, so it is also where contracts do their most important work. Two of them turn out to shape the class’s whole design.

Cells

A cell has a name, a formula, and a value. The value could always be recomputed from the formula, but recomputing every cell every time one is displayed would be wasteful, so each cell keeps its last computed value. That stored value is a cache, and like every cache, it is only useful while it agrees with what it caches:

class Cell
create
  make(n: String, f: Formula) do
    name := n
    formula := f
    value := create Num.make(0.0)
  end
feature
  name: String
  formula: Formula
  value: Value

  reads: Array[String] do
    result := references(formula.expr)
  end

  set_value(v: Value) do
    value := v
  end
invariant
  valid_name: is_cell_name(name)
end

A new cell starts at zero; the sheet will compute its real value as soon as the cell is stored. reads lists the cells its formula refers to, using references from Section 27.7.

The Sheet’s Contract

Before writing any of the sheet, it pays to do what Chapter 20 recommended: state what must be true, and let that shape the code. Two sentences describe a sheet that works:

  • no cell depends on itself, directly or through other cells
  • every cell holds the value of its formula

Neither is a property of one routine. Both must hold whenever anyone looks at the sheet, which makes them class invariants (Chapter 18):

invariant
  acyclic: is_acyclic
  consistent: is_up_to_date
end

Changing a cell is the operation that could break them, so its contract follows from them. Storing a formula that reads its own cell, or one that depends on it, would break acyclic in a way no recalculation could repair. So that is a precondition, and the caller must check it first, just as callers of the room calendar in Section 20.8 asked is_free before booking. consistent, on the other hand, is the sheet’s own job: after a change, it must recalculate whatever the change affects.

  set(name: String, f: Formula)
  require
    valid_name: is_cell_name(name)
    no_cycle: not would_cycle(name, f)
  do
    cells.put(name, create Cell.make(name, f))
    recalculate
  ensure
    stored: text_of(name) = f.text
  end

Like the calendar’s contract, this one names queries that do not exist yet: would_cycle, is_acyclic, is_up_to_date and text_of. Writing them is most of the rest of the chapter.

The Sheet’s State

The sheet keeps its cells in a map from name to cell. An empty cell is simply absent from the map, and reads as zero:

class Sheet
create
  make do
    cells := {}
    values := create Cell_Values.make(cells)
  end
feature
  cells: Map[String, Cell]
  values: Cell_Values

  count: Integer do
    result := cells.size
  end

  has(name: String): Boolean do
    result := cells.contains_key(name)
  end

  value_of(name: String): Value
  require
    valid_name: is_cell_name(name)
  do
    result := values.value_of(name)
  end

  text_of(name: String): String
  require
    valid_name: is_cell_name(name)
  do
    result := ""
    if has(name) then
      result := cells.get(name).formula.text
    end
  end

There is one surprise here. Formulas do not read their values from the sheet itself, but from values, a separate object that shares the sheet’s map and offers nothing but value_of:

-- What formulas see of a sheet: the values of its cells, and nothing else.
class Cell_Values inherit Cell_Source
create
  make(c: Map[String, Cell]) do
    cells := c
  end
feature
  cells: Map[String, Cell]

  value_of(name: String): Value do
    if cells.contains_key(name) then
      result := cells.get(name).value
    else
      result := create Num.make(0.0)
    end
  end
end

The sheet’s own value_of just asks this view. Why the sheet does not simply implement Cell_Source itself is the subject of Section 28.7; for now, it is enough that formulas see the values and nothing else.

Following Dependencies

A cell depends on another when its formula reads that cell, or reads a cell that depends on it. Following those links is a search, of the kind Chapter 19 wrote with loops: keep a list of cells still to look at, take one, and add the cells it reads.

  -- Does `name` read `other`, directly or through other cells?
  depends_on(name, other: String): Boolean
  require
    valid_names: is_cell_name(name) and is_cell_name(other)
  do
    result := false
    let seen: Set[String] := #{}
    let pending := reads_of(name)
    from until result or pending.is_empty do
      let next := pending.get(pending.length - 1)
      pending.remove(pending.length - 1)
      if next = other then
        result := true
      elseif not seen.contains(next) then
        seen.add(next)
        pending := pending.concat(reads_of(next))
      end
    end
  end

  reads_of(name: String): Array[String] do
    result := []
    if has(name) then
      result := cells.get(name).reads
    end
  end

The set seen stops the search from looking at any cell twice. That matters for speed when many cells read the same few, but it matters more for safety. is_acyclic will ask depends_on about every cell, and it is exactly the query that must give a sensible answer on a sheet that does contain a cycle, if there ever were one. A search that followed a cycle without remembering where it had been would never return.

With depends_on, the precondition of set can be written. A new formula for name creates a cycle if it reads name itself, or reads a cell that already depends on name:

  -- Would giving `name` this formula make it depend on itself?
  would_cycle(name: String, f: Formula): Boolean
  require
    valid_name: is_cell_name(name)
  do
    result := false
    across references(f.expr) as r do
      if r = name or depends_on(r, name) then
        result := true
      end
    end
  end

Recalculating in Order

When a cell changes, the cells that read it must be recalculated, and so must the cells that read those. The order matters: in the opening example, A3 reads A1 and B1 reads A3, so after a change to A1, recalculating B1 before A3 would add up a stale value.

The simplest correct rule is to recalculate every cell, each after the cells it reads. Producing that order is a depth-first walk: before adding a cell to the order, add everything it reads. Its postconditions say what an order must be, so that the walk checks itself:

  -- Every cell, each after the cells it reads.
  evaluation_order: Array[String] do
    result := []
    across cells.keys.sort as name do
      visit(name, result)
    end
  ensure
    every_cell_once: result.length = count
    reads_come_first: reads_come_first(result)
  end

  -- Does every cell in `order` come after the stored cells it reads?
  reads_come_first(order: Array[String]): Boolean do
    result := true
    across order as name do
      across reads_of(name) as r do
        if has(r) and order.index_of(r) > order.index_of(name) then
          result := false
        end
      end
    end
  end

  visit(name: String, order: Array[String]) do
    if has(name) and not order.contains(name) then
      across reads_of(name) as r do
        visit(r, order)
      end
      order.add(name)
    end
  end

  recalculate do
    across evaluation_order as name do
      let c := cells.get(name)
      c.set_value(evaluate(c.formula.expr, values))
    end
  ensure
    up_to_date: is_up_to_date
  end

visit has no explicit stopping test for cycles, and needs none: it follows the cells a formula reads, and the invariant acyclic promises that following them never leads back to where it started. This is an invariant doing more than catching mistakes. It is the reason an algorithm is correct. The order of cells has to exist, and the walk has to end, and both are true because of acyclic, which set’s precondition protects.

The postcondition of recalculate is the class’s second invariant, checked one more time at the point where it is established. The two queries behind the invariants are plain loops over the cells:

  -- Does every cell hold the value of its formula?
  is_up_to_date: Boolean do
    result := true
    across cells.values as c do
      if c.value /= evaluate(c.formula.expr, values) then
        result := false
      end
    end
  end

  -- Does no cell depend on itself?
  is_acyclic: Boolean do
    result := true
    across cells.keys as name do
      if depends_on(name, name) then
        result := false
      end
    end
  end

is_up_to_date is a strong check. It ignores how the values were computed and recomputes every one from scratch, so it would catch an evaluation order that was wrong, a cell left out, or a cell evaluated twice with a stale input. Recalculating everything is not the fastest strategy; Exercise 2 asks for one that recalculates only the cells a change affects. Whatever strategy replaces this one, the same postcondition will tell you whether it is right.

clear removes a cell and recalculates the rest; a cell that read it now reads zero:

  clear(name: String)
  require
    valid_name: is_cell_name(name)
  do
    cells.remove(name)
    recalculate
  ensure
    gone: not has(name)
  end

Using the Sheet

A small helper turns text into a Formula, raising if it is not one, which is enough for trying the sheet in the REPL:

nex> intern sheet/Sheet
nex> function formula(text: String): Formula do
       match parse_formula(text) of
         Ok as ok then result := ok.value
         Err as e then raise e.error
       end
     end
nex> let sheet := create Sheet.make
nex> sheet.set("A3", formula("A1 + A2 * 2"))
nex> show_value(sheet.value_of("A3"))
"0.00"
nex> sheet.set("A1", formula("120"))
nex> sheet.set("A2", formula("80"))
nex> show_value(sheet.value_of("A3"))
"280.00"
nex> sheet.set("B1", formula("SUM(A1:A3)"))
nex> show_value(sheet.value_of("B1"))
"480.00"
nex> sheet.depends_on("B1", "A1")
true
nex> sheet.depends_on("A1", "B1")
false
nex> sheet.evaluation_order
["A1", "A2", "A3", "B1"]
nex> sheet.would_cycle("A1", formula("B1 + 1"))
true
nex> sheet.set("A1", formula("B1 + 1"))
Error: Precondition violation: no_cycle
nex> sheet.text_of("A1")
"120"

A cell may be set before the cells it reads exist, as A3 was, and it is recalculated when they arrive. The cycle is refused by the precondition before anything changes, so A1 keeps its old formula. In the finished program, the command line will ask would_cycle first and print a message instead, so a user never sees a contract violation; the precondition is there for the programmer who forgets to ask.

Why the Sheet Is Not a Cell_Source

The natural first design lets the sheet be the source of its own values. It already has a value_of, so it can inherit Cell_Source and pass itself to the evaluator:

class Sheet inherit Cell_Source
...
  recalculate do
    across evaluation_order as name do
      let c := cells.get(name)
      c.set_value(evaluate(c.formula.expr, this))
    end
  ...

That version fails the first time one cell reads another. Setting A1 to 120 and then A2 to A1 * 2 stops with:

Error: Class invariant violation: consistent
  Sheet.value_of, called at line 29 of evaluate.nex, in evaluate, finds the invariant `consistent` of Sheet already broken on entry: the object was changed since its last check, by a call back into it mid-update or through a shared reference.
  called from line 31 of evaluate.nex, in evaluate
  called from line 159 of sheet.nex, in Sheet.recalculate
  called from line 109 of sheet.nex, in Sheet.set
  called from line 12

The message describes exactly what went wrong. set stored the new cell for A2, whose value starts at zero, and began recalculating. To compute A2, the evaluator asked the sheet for the value of A1. That call came from outside the class, from the function evaluate, so Nex checked the sheet’s invariant on entry, as it does for every call from outside (Chapter 18). And at that moment the invariant was false: A2 held zero, while its formula said 240.

Nothing was wrong with the invariant. Halfway through a recalculation, the sheet really is inconsistent; that is what recalculating means. What was wrong was the design, which let outside code call into the sheet while it was in that state. The rule an invariant imposes is stricter than it first appears: it must hold at every moment that a call can come in from outside, and a callback, a call into an object from code that the object itself called, comes in from outside.

There were two ways out. One weakens the contract: drop consistent from the invariant and make it a postcondition of set and clear instead. The other fixes the design, so that nothing calls back into the sheet while it is updating. The evaluator never needed the whole sheet; it needs values, and that is all Cell_Values gives it. Calls to the view check no invariant of the sheet, because they are not calls to the sheet. The sheet’s invariant now holds at every moment anyone outside can observe it, which is what an invariant should mean.

This is the interface segregation principle at work: a client should depend on an interface as narrow as what it uses. Here a contract found the reason for it.

The same rule explains one more detail of the code. The queries above, would_cycle, is_up_to_date and is_acyclic, are written with across loops, although any and all with a fn would be shorter. A fn reaches the sheet’s routines through the object it captured, so a routine called from inside one is called from outside the class, and the invariant is checked on entry. In reads_come_first, which runs in the middle of a recalculation, that check fails just as the evaluator’s did. A query that runs while the object is changing must call its own class’s routines directly, and a loop does.

What Contracts Cost

These contracts are expensive to check. is_up_to_date recomputes every cell, and it runs on entry to and exit from every call into the sheet from outside. is_acyclic searches the dependencies of every cell. On a sheet of a few dozen cells, nobody would notice. To see the cost, set 99 cells in a chain, each reading the one before, A2 = A1 + 1 to A99 = A98 + 1, and time the run twice: once as usual, and once with the --skip-contracts option, which runs the program with every require, ensure and invariant check removed (nex chain.nex --skip-contracts):

Setting 99 cells in a chainTime
Contracts checked13.8 s
--skip-contracts7.6 s

About 8 seconds of each run is Nex starting and compiling the program, so the contracts cost roughly six seconds for 99 changes, each followed by checks that recompute the whole sheet several times. An earlier version of this sheet, whose queries were written with all and any, needed more than five minutes for the same chain: every call from inside a fn re-checked the invariant, and each of those checks searched the dependencies of every cell.

The lesson is not that contracts are too expensive to use. Checked contracts found a real design error in the previous section, and they keep checking the evaluation order and every value while the program is being written and tested. For a sheet much larger than this one, run with --skip-contracts once it is tested; Exercise 4 of Chapter 24 asked when that is reasonable. But it is worth knowing where the cost comes from: an invariant is checked at every call from outside, so an object that receives many calls should have an invariant that is cheap to check, or few callers.

Summary

  • A cached value is only correct while it agrees with what it caches, which makes “agrees” a natural invariant
  • Properties that must hold whenever anyone looks are invariants; the contracts of the routines that change the object follow from them
  • A precondition the caller can check, like no_cycle, needs a query the caller can call, like would_cycle
  • An invariant can justify an algorithm: the dependency order exists, and the walk that finds it ends, because the sheet is acyclic
  • A postcondition that recomputes the answer, like is_up_to_date, checks any strategy that replaces the simple one
  • An invariant must hold whenever a call can arrive from outside, and a callback, or a call from inside a fn, arrives from outside
  • When an invariant fails mid-update, fix the design before weakening the contract; giving a client a narrower interface often does both
  • Checking contracts has a cost; measure it, and switch checking off with --skip-contracts once the program is tested, not before

Exercises

1. Write a query dependents(name: String): Array[String] that returns every cell that depends on name, directly or indirectly, in name order. Give it a postcondition stated with depends_on.

2. Recalculating every cell after every change is wasteful when a sheet is large. Write a version of set that recalculates only the changed cell and its dependents, still in dependency order. Keep the postcondition up_to_date, and use it to check your version against the original.

3. clear lets a user empty a cell that other cells read, which silently turns its value into zero in their formulas. Should clear have a precondition that nothing depends on the cell? Argue for one design, and say what the command line would have to do in each case.

4. Write a test that builds the chain A1 = B1, B1 = C1, and then checks that C1 = A1 is refused by would_cycle, and that setting it anyway violates the precondition no_cycle.

5. Draw a sheet in which depends_on, without its seen set, would look at the same cell many times. How many times, for a sheet of n cells arranged as you drew it?

6. Cell.set_value is a public routine. What could a client of the sheet do with it, which invariant would detect the damage, and at what moment? Redesign Cell so that its value cannot be changed from outside at all. What does the sheet do instead when a value changes?

7.* Measure the cost of contracts on your own machine, as in Section 28.8, for chains of 25, 50 and 99 cells. How does the extra time grow with the number of cells, and which contract accounts for most of it?
