Chapter 25

Testing Your Programs

Contracts improve correctness, but they do not remove the need for tests. A contract states what must be true on every call. A test picks particular calls and checks what actually happens. This chapter is about writing tests in Nex: how to check results, how to check that a contract refuses a bad call, how to test code that depends on the outside world, and how to keep a program’s tests in one place where they can be run at any time.

What Tests Add

Section 20.5 drew the line between the two: the contract defines the law, and tests exercise representative cases under it. Tests catch what contracts tend to miss:

  • a boundary case the programmer forgot
  • a wrong algorithm that still satisfies a weak postcondition
  • a problem that appears only when several routines are used together
  • a regression, where a later change breaks something that used to work

The last of these is the strongest reason to write tests down. A test you ran once by hand protects nothing. A test kept in a file and run after every change keeps protecting the program for as long as it exists.

Test Small Things First

The best starting point is the smallest meaningful unit. For a function:

nex> function square(x: Integer): Integer
     do
       result := x * x
     end

simple tests might be:

nex> square(0)
0

nex> square(5)
25

nex> square(-3)
9

The three calls are chosen to exercise the routine’s meaning, not picked at random:

  • a neutral case (0)
  • a typical case (5)
  • a case that might surprise (-3, whose square is positive)

A Tiny Test Harness in Nex

Checking results by eye works once. To make the checks repeatable, write them down as code. Nex needs no testing framework for this, because the check is already in the language. The assert statement states what must be true at the point it appears, and raises an Assertion_Violation when it is not:

nex> function test_square()
     do
       assert square_zero: square(0) = 0
       assert square_positive: square(5) = 25
       assert square_negative: square(-3) = 9
       print("square tests passed")
     end

The label before the colon names the case, and it is what a failure reports:

Error: Assertion violation: square_positive

When a name would only repeat the expression, the label may be left out, and the failure reports the line instead, such as Assertion violation (line 18).

Because a failed assert raises an exception, the first failing case stops the test. That is usually what you want: fix the first failure, then run the tests again.

An assertion says that a check failed, not what the values were. When the values would help, as they usually do for a comparison, write a small helper whose message includes them:

nex> function assert_equal(actual, expected: Integer, label: String)
     do
       if actual /= expected then
         raise label + ": expected " + expected.to_string + ", got " + actual.to_string
       end
     end

nex> assert_equal(square(3), 6, "square three")
Error: square three: expected 6, got 9

The message now says everything needed to start looking for the bug. A helper is worth writing only when it reports more than assert would. A helper that just checks a condition adds nothing, because assert already does that.

Testing Contracts

A test should also check that a contract does its job: that a bad call is refused, at the place it should be. The examples in this section and the next use the Stack from Section 17.8, whose pop has the precondition not_empty:

nex> class Stack [G]
     create
       make
       do
         items := []
       end
     feature
       items: Array[G]

       push(value: G)
       do
         items.add(value)
       ensure
         last_is_value: items.get(items.length - 1) = value
       end

       pop: G
       require
         not_empty: items.length > 0
       do
         result := items.get(items.length - 1)
         items.remove(items.length - 1)
       ensure
         length_decreased_by_one: items.length = old items.length - 1
       end
     end

To test that pop on an empty stack is refused, make the call and catch what it raises. A contract violation arrives in rescue as an object of a built-in class (Section 21.6):

nex> function test_pop_on_empty_stack_is_refused()
     do
       let s := create Stack[Integer].make
       let popped := s.pop
       raise "pop on an empty stack returned " + popped.to_string
     rescue
       if convert exception to v: Precondition_Violation then
         assert refused_by_not_empty: v.label = "not_empty"
         print("empty-pop test passed")
       else
         raise exception
       end
     end

nex> test_pop_on_empty_stack_is_refused()
"empty-pop test passed"

The test covers each way things could go wrong:

  • If pop returns a value instead of failing, the raise after it reports that, and the test fails.
  • If pop fails for some other reason, the exception is not a Precondition_Violation, and the else branch raises it again, so the test fails with the real cause.
  • If a precondition fails but it is the wrong one, the assert on v.label fails. A different precondition being violated would be a different bug, and the test should say so.

Only if pop is refused by not_empty itself does the test pass.

Testing Classes Through Sequences

A class keeps state between calls, so most of its behaviour shows only across several calls in a row. A stack is the clearest case: its whole point is the order in which values come back.

nex> function test_stack_order()
     do
       let s := create Stack[Integer].make
       s.push(1)
       s.push(2)
       s.push(3)
       assert_equal(s.pop, 3, "last in")
       assert_equal(s.pop, 2, "then the one before")
       s.push(9)
       assert_equal(s.pop, 9, "a later push comes off first")
       assert_equal(s.pop, 1, "first in, last out")
       assert empty_again: s.items.is_empty
       print("stack order tests passed")
     end

nex> test_stack_order()
"stack order tests passed"

No single call here proves anything. The sequence does: it mixes pushes and pops, so an implementation that took values from the wrong end, or lost one in the middle, would fail one of the checks. The contracts on push and pop are checked on every call as well, so the test exercises them too.

Choosing Good Test Cases

Good tests cover different kinds of behaviour:

Normal cases: ordinary, expected inputs, to show that the routine does its job at all.

Boundary cases: an empty array, a one-element array, zero, the largest and smallest allowed values, and the value exactly at a dividing line. Bugs gather at boundaries, because that is where < and <= differ.

Some boundary cases come from how the code works rather than from what it promises. "to be".split(" ") gives ["to", "", "be"]: two spaces in a row leave an empty piece between them. A routine that counts words by splitting on spaces therefore needs a test with repeated spaces, or it may count the empty string as a word without anyone noticing. A test like that also protects the fix: once the routine skips empty pieces, the test keeps it that way after later changes.

Error cases: calls that a contract should refuse, tested as in Section 25.4.

Sequences: for classes, runs of operations that take an object through its states.

A common mistake is to test only the normal case. Tests become valuable at the boundaries and in the cases that should fail.

Testing Code That Touches the Outside World

Some code depends on things a test cannot control like the network or a random number generator. Consider a greeting that depends on system time:

nex> intern time/Date_Time

nex> deferred class Clock
     feature
       hour: Integer
       deferred
     end

nex> class System_Clock inherit Clock
     feature
       hour: Integer
       do
         result := create Date_Time.now().hour()
       end
     end

nex> function greeting(clock: Clock): String
     require
       valid_hour: 0 <= clock.hour and clock.hour < 24
     do
       let h := clock.hour
       if h < 12 then
         result := "Good morning"
       elseif h < 18 then
         result := "Good afternoon"
       else
         result := "Good evening"
       end
     end

Had greeting read the time itself, it could only be tested by running the test at different times of day. Instead it receives a Clock. The program passes a System_Clock, which reads the real time. A test passes a clock it controls:

nex> class Fixed_Clock inherit Clock
     create
       make(h: Integer)
       do
         fixed_hour := h
       end
     feature
       fixed_hour: Integer
       hour: Integer
       do
         result := fixed_hour
       end
     end

nex> function test_greeting()
     do
       assert morning: greeting(create Fixed_Clock.make(9)) = "Good morning"
       assert noon: greeting(create Fixed_Clock.make(12)) = "Good afternoon"
       assert evening: greeting(create Fixed_Clock.make(18)) = "Good evening"
       assert midnight: greeting(create Fixed_Clock.make(0)) = "Good morning"
       print("greeting tests passed")
     end

Fixed_Clock is a fake: a real implementation of the abstraction, written for testing, that does no more than the test needs. With it, the test can check exactly the hours that matter: a normal morning, the boundaries at 12 and 18, and midnight.

This is the same design that Chapter 24 recommended for Java: keep the code that touches the outside world small and behind an abstraction, and the rest of the program can be tested with ordinary values. Chapter 27 will use a fake in the same way to test spreadsheet formulas without a spreadsheet.

Organizing and Running Tests

Tests are only useful if they get run, and they get run only if that is easy. A simple arrangement that works well is to keep the program’s tests in one file, tests.nex, next to the program:

greeter/
  main.nex
  tests.nex
  lib/greeting/Greeting.nex

Greeting.nex holds Clock, System_Clock and greeting. main.nex is the program itself. tests.nex interns the same module, defines what only the tests need, and calls each test function at the end:

intern greeting/Greeting

class Fixed_Clock inherit Clock
create
  make(h: Integer)
  do
    fixed_hour := h
  end
feature
  fixed_hour: Integer
  hour: Integer
  do
    result := fixed_hour
  end
end

function test_greeting()
do
  assert morning: greeting(create Fixed_Clock.make(9)) = "Good morning"
  assert noon: greeting(create Fixed_Clock.make(12)) = "Good afternoon"
  assert evening: greeting(create Fixed_Clock.make(18)) = "Good evening"
  assert midnight: greeting(create Fixed_Clock.make(0)) = "Good morning"
  print("greeting tests passed")
end

test_greeting()
print("all tests passed")

The fake lives in tests.nex, not in the library. It exists for the tests, and the program has no use for it. Running the tests is one command:

$ nex tests.nex
"greeting tests passed"
"all tests passed"

Suppose a later change slips in an off-by-one error, so that 6 p.m. is still called afternoon (h <= 18 instead of h < 18). The next run names the case that broke, and the line of the test:

$ nex tests.nex
Error: Assertion violation: evening
  at line 21, in test_greeting
  called from line 26

As the program grows, add one test_… function for each part of it, and a call to each at the bottom of tests.nex. The first failure stops the run. For a program of this size that is fine: fix it, and run the tests again. Run them after every change, and they will catch regressions while the change is still fresh in your mind.

Summary

  • Contracts state the law, and tests check particular cases under it; tests also catch regressions after later changes
  • The built-in assert statement, with a label naming the case, is enough to begin. Write a helper only when its message should carry the values involved
  • Test that a contract refuses a bad call by catching the Precondition_Violation and checking its label, and re-raise anything else
  • Test classes through sequences of operations
  • Cover boundary and error cases, not only normal ones
  • Code that depends on the outside world should receive it through an abstraction, so a test can pass a fake
  • Keep a program’s tests in tests.nex and run them with nex tests.nex after every change

Exercises

1. Write an assert_equal_string helper whose message shows both strings, and use it to test a reverse(s: String): String function, including the empty string and a one-character string.

2. Add a peek query to the Stack of this chapter, with a precondition. Write tests for it: one that checks it returns the top value without removing it, and one that checks it is refused on an empty stack.

3. Design a test sequence for the Account class of Chapter 16 that checks deposit, withdrawal, a transfer, and one call that should be refused.

4. Write test_word_frequencies for the word_frequencies routine of Chapter 10. Include an ordinary sentence, words that differ only in case, repeated spaces, an empty string and a string of only spaces. Some of these tests will fail. Find out why, fix the routine, and run the tests again.

5. A dice game rolls a die with Random. Put the roll behind a deferred class Die, write a fake that returns rolls from a fixed list, and use it to test the rule that a double six wins.

6.* Pick one routine whose contract is weaker than what it really promises. Write tests that would catch an incorrect implementation that the current postcondition would let through.
