Chapter 22

Writing Robust Code

The last chapter covered the tools for handling failure: raise, rescue, retry, exception classes, and result types. This chapter is about where to use them in a program. Every failure raises two design questions: where should it be noticed, and what state should the program be left in afterwards?

Robust code is not code that never fails. It is code that fails in the right place and diligently reports what happened. The chapter works through one small program, a booking system for a theatre, and builds it in layers. Untrusted input is checked at the edge, contracts protect the inside, and an operation that fails leaves nothing behind.

Three Kinds of Failure

The earlier chapters have already sorted failures into three kinds. Each kind calls for its own response:

  • Caller mistakes, such as booking more seats than are left, are contract violations. A precondition catches them at the call that made the mistake (Chapter 16).
  • Routine bugs, where a routine does not do what it promised, show up as failed postconditions or invariants (Chapters 17 and 18).
  • Failures of the outside world, such as a file that can't be written or input that makes no sense, happen even when every part of the program is correct. They call for exceptions or result types (Chapter 21).

For the first two kinds, the right response is to fail fast: stop at once, at the place where the mistake was made. Carrying on with a made-up value hides the original bug and adds new damage of its own. Only the third kind is something a program should expect, plan for, and recover from. Most bad error handling comes from mixing these up, for example by treating a caller’s bug as bad luck, or by treating an ordinary event like a customer typo as a crisis.

Check Once, at the Boundary

A customer asks for seats by typing a line such as ana 4: a name followed by a number of seats. That line comes from outside the program, so anything can be in it. As Chapter 16 explained, bad input from outside is not a contract violation. It is an ordinary event, and the program must handle it.

The pattern is to check the input once, where it enters the program, and turn it into a value that cannot be wrong. Everything further in then works with that clean value and can rely on contracts.

The clean value is a small class whose invariant states what a valid request is:

nex> class Request
     create
       make(n: String, c: Integer)
       require
         has_name: n.length > 0
         positive_count: c > 0
       do
         name := n
         count := c
       end
     feature
       name: String
       count: Integer
     invariant
       has_name: name.length > 0
       positive_count: count > 0
     end

Because of the invariant, a Request with no name or with zero seats cannot exist. Any routine that receives a Request knows it is valid without checking again. This is what “make invalid states unrepresentable” means: the type carries the guarantee.

The code at the boundary turns text into a Request. Text that doesn’t make sense is a normal outcome here, so these routines return a Result (Section 21.9) rather than raising an exception:

nex> intern data/Result

nex> function parse_count(text: String): Result[Integer, String]
     do
       let n := text.to_integer
       if n > 0 then
         result := create Ok[Integer, String].make(n)
       else
         result := create Err[Integer, String].make("the number of seats must be positive")
       end
     rescue
       result := create Err[Integer, String].make(text + " is not a number")
     end

nex> function parse_request(line: String): Result[Request, String]
     do
       let words := line.split(" ")
       if words.length /= 2 or words.get(0).length = 0 then
         result := create Err[Request, String].make("expected a name and a number of seats")
       else
         match parse_count(words.get(1)) of
           Ok(value) then
             result := create Ok[Request, String].make(create Request.make(words.get(0), value))
           Err(error) then
             result := create Err[Request, String].make(error)
         end
       end
     end

Look at the rescue in parse_count. When to_integer is given text like three, it raises a Conversion_Error. At the boundary, that exception is turned into an ordinary Err, because a customer typing a word instead of a number is not exceptional. Every way the input can be wrong is handled here, and each one gets a message the customer can understand:

nex> across ["ana 4", "ben three", "cy 0", "dee"] as line do
       match parse_request(line) of
         Ok(value) then print(value.name + " wants " + value.count.to_string)
         Err(error) then print("rejected: " + error)
       end
     end
"ana wants 4"
"rejected: three is not a number"
"rejected: the number of seats must be positive"
"rejected: expected a name and a number of seats"

As you can see, the boundary code is extra careful. If parse_request ever called Request.make with an empty name, the precondition would stop it. That would be a bug in parse_request, not bad input.

A Class That Protects Itself

Inside the boundary, a Show keeps track of its seats. It records each customer’s booking and saves the bookings to a file, so they survive a restart:

nex> intern io/Path

nex> class Show
     create
       make(seats: Integer, file: Path)
       require
         some_seats: seats > 0
       do
         capacity := seats
         free := seats
         bookings := {}
         store := file
       end
     feature
       capacity: Integer
       free: Integer
       bookings: Map[String, Integer]
       store: Path

       booked(): Integer
       do
         across bookings.values as n do
           result := result + n
         end
       end

       to_text(): String
       do
         across bookings.keys as name do
           result := result + name + " " + bookings.get(name).to_string + "\n"
         end
       end

       book(name: String, count: Integer)
       require
         positive_count: count > 0
         enough_seats: count <= free
         new_customer: not bookings.contains_key(name)
       do
         free := free - count
         bookings.set(name, count)
         store.write_text(to_text())
       end
     invariant
       free_in_range: 0 <= free and free <= capacity
       all_seats_accounted: free + booked() = capacity
     end

The invariant all_seats_accounted says that every seat is either free or booked by someone, never both and never neither.

enough_seats and new_customer deserve a closer look. A customer asking for more seats than are left is perfectly normal, so why are these preconditions and not exceptions? The reason is that the caller can check them. Both conditions depend only on free and bookings, which any caller can read. A caller that wants to book seats can look before it asks. If it doesn’t look, that is the caller’s bug:

nex> let show := create Show.make(10, create Path.make("bookings.txt"))

nex> show.book("ana", 4)

nex> show.free
6

nex> show.book("ben", 7)
Error: Precondition violation: enough_seats

The one thing in book that no caller can check in advance is whether the file can be written. That is a failure of the outside world, and it is where this version of book has a flaw.

Guarding Against Partial Updates

Suppose the file is in a folder that doesn’t exist:

nex> let show := create Show.make(10, create Path.make("/no-such-folder/bookings.txt"))

nex> show.book("ana", 4)
Error: /no-such-folder/bookings.txt (No such file or directory)

nex> show.free
6

nex> show.bookings
{"ana": 4}

The call failed, and the caller was told it failed. But the seats are gone anyway. book changed free and bookings before it tried to save, and nothing changed them back. Now see what happens when Ana tries again, as anyone would after a failure:

nex> show.book("ana", 4)
Error: Precondition violation: new_customer

The show insists that Ana already has a booking, which nobody ever confirmed to her. Notice that no invariant caught the problem. The show is consistent with itself, because its free seats and its bookings still add up. What it disagrees with is the file and the caller. This is a partial update: an operation that failed partway through and left some of its changes behind.

The rule is simple to state: an operation that reports failure must leave everything as it was. There are two ways to keep it.

Do the risky step first

Put the step that might fail before any change to the object. Work out what the file should contain once the booking is made, and write that first. Change the fields only after the write has succeeded:

book(name: String, count: Integer)
require
  positive_count: count > 0
  enough_seats: count <= free
  new_customer: not bookings.contains_key(name)
do
  store.write_text(to_text() + name + " " + count.to_string + "\n")
  free := free - count
  bookings.set(name, count)
end

If the write fails, nothing has been changed yet, so there is nothing to undo. The two changes after it cannot fail, because the preconditions have already ruled out every way they could go wrong. This order, where everything that might fail comes first and then all the changes, is the better fix whenever it is possible.

Undo in the rescue clause

Sometimes the risky step has to come last. The original book is an example, since to_text can only describe the new state once that state exists. In that case, the rescue clause can undo the changes and then re-raise, so the caller still learns about the failure:

book(name: String, count: Integer)
require
  positive_count: count > 0
  enough_seats: count <= free
  new_customer: not bookings.contains_key(name)
do
  free := free - count
  bookings.set(name, count)
  store.write_text(to_text())
rescue
  free := free + count
  bookings.remove(name)
  raise exception
end

This works because the only step that can fail is the last one. By the time anything can go wrong, both changes have been made, and the rescue clause knows exactly what to undo. In a routine with failure points scattered through it, the rescue clause would have to work out how far the body got before it failed. That is hard to get right, and it is the main reason to prefer the first fix.

With either version of book in the class, a failed save leaves the show exactly as it was:

nex> let show := create Show.make(10, create Path.make("/no-such-folder/bookings.txt"))

nex> show.book("ana", 4)
Error: /no-such-folder/bookings.txt (No such file or directory)

nex> show.free
10

nex> show.bookings
{}

Where the Failures Meet

The last piece is a booking desk: the routine that connects a customer’s line of text to the show. Every kind of failure in this chapter can reach it, but as they are already segregated in the lower layers, this final routine can have a clean and simple design:

nex> function handle_request(show: Show, line: String): String
     do
       match parse_request(line) of
         Ok(value) then
           if value.count > show.free then
             result := "rejected: only " + show.free.to_string + " seats left"
           elseif show.bookings.contains_key(value.name) then
             result := "rejected: " + value.name + " already has a booking"
           else
             show.book(value.name, value.count)
             result := "booked " + value.count.to_string + " for " + value.name
           end
         Err(error) then
           result := "rejected: " + error
       end
     rescue
       if convert exception to h: Host_Exception then
         result := "not booked, could not save: " + h.message
       else
         raise exception
       end
     end

Each kind of failure is handled in its own place:

  • Bad input never gets past parse_request. The desk receives an Err and passes its message on to the customer.
  • Requests that are valid but can’t be met, such as too many seats or a second booking, are checked by the desk before it calls book. These are the preconditions of book, and the desk tests them in advance as a careful caller should.
  • A failed save reaches the rescue clause as a Host_Exception. The desk can sincerely tell the customer “not booked”, because book guarantees that a failed booking leaves no trace.
  • Anything else is re-raised. A contract violation here would mean the desk itself has a bug, for example a missing check before book. Reporting that as “try again later” would hide it.

A run of requests shows every path:

nex> let show := create Show.make(10, create Path.make("bookings.txt"))

nex> across ["ana 4", "ben three", "cy 0", "dee", "ana 2", "eve 7", "eve 6"] as line do
       print(line + " -> " + handle_request(show, line))
     end
"ana 4 -> booked 4 for ana"
"ben three -> rejected: three is not a number"
"cy 0 -> rejected: the number of seats must be positive"
"dee -> rejected: expected a name and a number of seats"
"ana 2 -> rejected: ana already has a booking"
"eve 7 -> rejected: only 6 seats left"
"eve 6 -> booked 6 for eve"

nex> show.store.read_text
"ana 4
eve 6
"

And when the file can’t be written:

nex> let broken := create Show.make(10, create Path.make("/no-such-folder/bookings.txt"))

nex> handle_request(broken, "ana 4")
"not booked, could not save: /no-such-folder/bookings.txt (No such file or directory)"

nex> broken.free
10

None of the routines is complicated. The program is robust because each one has a clear job: parse_request handles input it can’t trust, Request and Show use contracts to refuse anything invalid, book either does everything or nothing, and the desk turns each outcome into a reliable answer.

Habits of Robust Code

The booking system follows a few habits that are worth keeping in any program:

Check untrusted data once, at the edge, and turn it into a type whose invariant guarantees it is valid. Code further in should not have to check it again.

Make the preconditions things a caller can check. A precondition that depends only on what the caller can see, such as count <= free, tells the caller exactly what to test first.

Do everything that might fail before changing anything. When that isn’t possible, undo the changes in rescue and re-raise.

Recover reliably. A fallback is acceptable only if it is announced and its meaning is documented. Returning an empty string when a file fails to load, for example, is a lie if callers will read it as “the file was empty”.

Catch only what you can handle. Name the exception class you expect, and re-raise everything else, so that bugs still surface as bugs.

Use detachable types only when absence is meaningful. Don’t reach for ?Type just to avoid deciding what should really be required.

Summary

  • Caller mistakes and routine bugs should fail fast through contracts. Only failures of the outside world are things to plan for and recover from
  • Check untrusted input once, at the boundary, and turn it into a value whose invariant guarantees it is valid
  • At the boundary, bad input is a normal outcome: return a result instead of raising
  • Preconditions work best when the caller can check them before calling
  • An operation that reports failure must leave everything as it was. Do the risky step first, or undo the changes in rescue and re-raise
  • Handle each kind of failure where it can be handled meaningfully, and let the rest propagate

Exercises

1. Take one routine from an earlier chapter and sort its possible failures into caller mistakes, routine bugs, and failures of the outside world.

2. parse_request rejects ana  4, which has two spaces in the middle. Change it to accept extra spaces between and around the two words. Then make it reject names that contain digits. Which of these checks belongs in parse_request, and which, if any, belongs in the invariant of Request?

3. Remove the free-seats check from handle_request and send it the line eve 20. What does Nex report? Explain why that is the right kind of failure for this mistake, and why handle_request should not catch it.

4. Add a routine cancel(name: String) to Show that removes a booking, frees its seats, and saves the file. Write its precondition, and make sure a failed save leaves the show exactly as it was. Which of the two fixes from Section 22.4 did you use, and why?

5.* A program updates two files that must always match, such as a list of bookings and a list of payments. Sketch a design for this operation. Where would you put contracts, where would you use exceptions, and how would you keep a failure while writing the second file from leaving the two files inconsistent?
